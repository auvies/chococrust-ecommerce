# ADR 0009: Payment, COD, Inventory, and Delivery

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 09 needed to harden four modules that already existed in outline since Phase 02/04/08: payment status as its own vocabulary (`COD_PENDING`/`COD_CONFIRMED`/`COD_COLLECTED`/`PAID`/`FAILED`/`REFUNDED`) tracked independently of order fulfillment status, the full COD flow through a `Completed` order state, real "available/reserved/sold/released" inventory tracking with history, richer delivery tracking (attempts, failed delivery, customer refused, return to seller), config-driven payment methods (COD, Easypaisa, JazzCash, future gateways) with a hard rule that nothing sensitive (PIN/OTP/password/credentials/API secrets) ever reaches the frontend, idempotency for every payment-sensitive operation, and an explicit guarantee that AI never independently verifies a payment.

## Decisions

### Native DB enums were the wrong tool the moment the business's status vocabulary grew again

`payments.status`, `orders.status`, and `inventory_reservations.status` were all native enums. This phase alone needed `payments.status` to grow from 7 values to include `cod_pending`/`cod_confirmed`/`cod_collected`, `orders.status` to add `ready`/`completed`, and `inventory_reservations.status` to add `fulfilled` — a native enum needs a schema migration for every such addition, and this sandbox has no `doctrine/dbal` installed (needed for Laravel's `->change()` on an existing column), and no network access to install it (ADR 0003's own constraint, recurring). Rather than fight that, all three columns were converted to plain indexed strings via a new migration (`Schema::table` drop-index/drop-column/add-column/add-index, four small calls instead of one `->change()` — SQLite refuses to drop a column that's still part of an index, so the index has to go first) — matching the precedent `payments.method` already set (see its own migration comment: "shouldn't require a migration to add"). Validation moved entirely to the application layer: Form Requests bound to `in:...`/`Rule::in(config(...))`, and `OrderService::TRANSITIONS` as the actual authority on legal *transitions*, not just legal values. `deliveries.status`/`cod_records.status` were left as native enums deliberately — their vocabularies didn't need to grow this phase, and converting them preemptively would be exactly the kind of speculative change CLAUDE.md warns against.

### The COD flow maps across three state machines, not into one

The business's brief (Order Created → Inventory Reserved → COD Pending → Confirmed → Processing → Ready → Dispatched → Out for Delivery → Delivered → COD Collected → Completed) reads like a single linear pipeline, but "separate ORDER STATUS from PAYMENT STATUS" is an explicit, harder requirement, and CLAUDE.md's own database design already committed to three independent state machines (`orders.status`, `payments.status`, `cod_records.status`). The resolution: order status gained `ready`/`completed`; payment status gained the three COD-specific states; and `OrderService::transitionStatus()` triggers side effects on the *other* two machines only at the three points the business flow itself implies a cross-cutting change — confirming an order commits its reservations and bumps a COD payment to `cod_confirmed`; delivering one fulfills those reservations; cancelling one releases them and moves a still-in-flight payment to `cancelled` (never downgrading one that's already settled). Nothing else about order status ever touches payment status, and nothing about payment status ever touches order status — `OrderService`'s own docblock says this explicitly now.

### `collectCod()` and `verifyCod()` needed to stop looking identical to the payment status

Before this phase, `collectCod()` (a rider's own claim that cash changed hands) left `payments.status` untouched — only `verifyCod()` (staff reconciling the cash) ever set anything, straight to `paid`. That meant a "Delivered COD" admin dashboard view had no way to distinguish "a rider says they collected it" from "nobody's touched this yet" by looking at payment status alone. `collectCod()` now moves payment status to `cod_collected`; `verifyCod()` is still the only thing that ever sets `paid`, preserving the existing, deliberate distinction between a rider's claim and staff verification (CLAUDE.md §5: "Refund and payment-status-changing actions require an authenticated admin with the correct role... always audit-logged" — collection alone was never meant to be sufficient).

### Two new PaymentService methods for outcomes that previously had nowhere to go

"Failed delivery," "customer refused," and "return to seller" existed as `deliveries.status` values (`failed`/`returned`) and one `cod_records.status` value (`failed_collection`), but nothing connected a failed/returned *delivery* to the *payment* it was for — a COD order that never got delivered would sit at `cod_pending` forever, indistinguishable from one still in progress. `PaymentService::markCodFailed()` and `markCodReturned()` move the COD record and its payment together (to `failed_collection`/`returned` and `failed` respectively), and `DeliveryController::updateStatus()` calls `markCodReturned()` automatically when a delivery is marked `returned`, so staff updating the delivery side don't have to separately remember the payment side. `markCodReturned()` never downgrades a payment that's already `paid`/`refunded`/`partially_refunded` - an edge case (a return recorded after the fact) that's easy to get wrong if you don't deliberately guard for it.

### `InventoryService`: the sell-through half of the lifecycle that never existed

Reading `OrderService`/`priceLines()` closely surfaced a real gap, not a hypothetical one: `inventory_reservations.status` had a `committed` value that nothing in the codebase ever set (every reservation stayed `pending` until `released` or forgotten), and `quantity_on_hand` never decreased when an order was actually delivered - there was no code path that turned a reservation into a sale at all. "Available/Reserved/Sold/Released" (the business's own checklist) maps directly onto a real lifecycle only once that gap closes: `reserve` (hold stock, still available-to-others is reduced), `commit` (a harder hold - order confirmed, no status change to on-hand yet), `release` (hold undone, back to available), `fulfill` (the hold becomes permanent - `quantity_on_hand` decrements, the reservation moves to a new `fulfilled` status, and *that* sum is "sold stock"). Every method is a `lockForUpdate()` transaction reading the same on-hand/reserved figures `OrderService::priceLines()` already computed - two concurrent checkouts for the last unit of stock can't both succeed, because the second transaction blocks on the row lock until the first commits, then re-reads a figure that already excludes it. `OrderService` was refactored to call this service instead of creating/updating `InventoryReservation` rows directly, and `InventoryController::adjust()` now routes through it too, so a manual stock correction gets the same lock and the same history record as every other movement.

### "Inventory history" is a dedicated table, not another use of `audit_logs`

`audit_logs` already exists and already captures `inventory.adjusted` events, but it mixes every admin action across every module (product edits, role changes, refunds, ...) - not a useful place to ask "show me everything that happened to this variant's stock." `inventory_movements` (new, append-only, same shape as `delivery_tracking_events`/`order_status_histories`) records every reservation created/committed/released/expired, every sale fulfilled, and every manual adjustment, each with a signed `quantity_delta` and an optional `order_id`/`reservation_id`/reason - queryable per variant via a new `GET /inventory/{id}/history` endpoint and an admin "History" modal.

### Payment methods live in `config/payments.php`, not a migration or an enum

"Future payment gateways" needed to mean something concrete without building a fake integration. `config('payments.methods')` is the allow-list `StoreOrderRequest` validates `payment_method` against (`Rule::in(...)`) - adding a gateway is a one-line config change. Only `cod` is a live, working flow. Selecting `easypaisa`/`jazzcash` is possible (the checkout page shows them, disabled, labeled "Coming soon") and creates a `Payment` row at the generic `pending` status - deliberately not a fabricated "paid" or a fake OTP/redirect screen, since neither gateway has an actual account/API key behind it (CLAUDE.md §6: secrets live in environment variables that don't exist yet for these) and building either honestly requires webhook signature verification (CLAUDE.md §5) that has nothing to verify against right now. This mirrors how MFA was handled in Phase 03 (ADR 0003): the data model and status machine are ready; the live integration is deliberately a later phase's work, not a shortcut taken now.

### AI's exclusion from payment verification is now written down, not just structurally true

`AiToolService` was already read-only and its `get_order_status` tool already only ever touched `orders.status` - it never had a path to `payments`/`cod_records` in the first place. That was true by omission, not by declared policy. The service's docblock now says explicitly that payment/COD verification is permanently out of scope (not deferred the way order-placing/refunding is, which the same docblock already flagged as "a deliberate follow-up, not an oversight") - a future contributor adding a tool has to actively contradict a stated rule to violate this, not just fail to notice an implicit one.

### Idempotency extended to the two COD actions that needed it and didn't have it

Refunds were already idempotent (Phase 04). `collectCod()`/`verifyCod()` were not - a retried request (a flaky rider's connection, a double-tap) would have double-processed a cash collection or a verification. All four COD mutations (`collect`, `verify`, and the two new ones, `fail`/`return`) now require an `Idempotency-Key` header via the same `idempotent` middleware `POST /orders` and refunds already use; `lib/api/admin/payments.ts` generates a fresh key per click, mirroring the existing refund pattern rather than inventing a new one.

### Concurrency is tested as the check-then-act guard, not literal threads

PHPUnit has no real parallelism, so "two requests racing" is tested the way the guarantee actually holds in production: two sequential calls with genuinely different actors and idempotency keys (so neither short-circuits into a replay), asserting the second is rejected by the state check *inside* the transaction. `test_two_reservations_racing_for_the_last_units_the_second_is_rejected` and `test_two_concurrent_collect_attempts_with_different_keys_the_second_is_rejected` are the two direct examples - this is the same correctness property `lockForUpdate()` provides under genuine parallel requests, since the guard logic being tested doesn't change based on whether the two calls happen to overlap in wall-clock time.

### A real bug caught by manual code review, not a test run - again

This session's sandbox still has no PHP 8.4+ runtime (ADR 0007/0008's recurring constraint), so all 32 new tests were traced by hand. That trace caught a genuine bug before it would have silently broken every new test: `UpdateOrderStatusRequest`'s validation rule still hardcoded `in:confirmed,processing,dispatched,delivered,cancelled,refunded` from before this phase added `ready`/`completed` to `OrderService::TRANSITIONS`. Every lifecycle test exercising those two new statuses would have failed at the 422 validation layer before ever reaching the service logic under test - a failure mode indistinguishable from "the transition graph is broken" unless traced deliberately. Fixed by updating the allow-list to the service's real vocabulary. Every touched file was also run through `php -l` (syntax-only, using a PHP 8.1 binary present in the sandbox) - a partial but genuine execution-based check on top of the trace, not available in Phase 07/08.

## Consequences

- Backend: one migration converting `orders`/`payments`/`inventory_reservations` status columns from enums to strings and adding `deliveries.delivery_attempts`/`failure_reason`; a new `inventory_movements` table/model/resource; a new `InventoryService`; `OrderService` and `PaymentService` extended with the cross-machine side effects and two new COD outcomes; `config/payments.php`; four new/changed routes (`PATCH /cod-records/{id}/fail`, `/return`, `GET /inventory/{id}/history`, plus idempotency added to `collect`/`verify`). 32 new backend tests (9 `PaymentTest`, 10 `InventoryTest`, 5 `DeliveryTest`, 8 `OrderTest`) - 222 backend tests total, written and manually traced but not executed for the same PHP-runtime reason as ADR 0007/0008 (confirmed via `php -l` syntax checking instead).
- Frontend: a payment-method selector on checkout (COD live, others shown disabled); filtered dashboard views ("Paid"/"Pending"/"Failed" on Payments, "COD Orders"/"Delivered COD"/"Failed"/"Returns" on COD, "Failed delivery"/"Returns" on Delivery) via a new array-valued `filter[col][]=` query-string capability and a small `FilterTabs` component; an inventory "History" view; richer `StatusBadge` tones for the new statuses. 1 new frontend test (63 total, all executed and passing), plus `typecheck`/`lint`/`build` green.
- Deliberately out of scope: the actual Easypaisa/JazzCash gateway integration (redirect flow, webhook signature verification, reconciliation) - the data model and status machine are ready, per the "config, not a migration" decision above; a dedicated inventory expiry sweep for stale `pending` reservations (the `expires_at` column exists from Phase 02 but nothing consumes it yet - a scheduled job is a natural, separate follow-up, not silently bundled into this phase).
