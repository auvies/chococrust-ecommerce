# ADR 0008: Cart, Checkout, and Delivery Eligibility

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 08 needed a full customer-facing order flow — cart, quantity, variants, per-item customization, address management, delivery eligibility, checkout, order creation/confirmation, a status timeline, order history, and tracking — plus configurable local-delivery rules for a new fresh-goods product line (Cakes, Pastries, Pizza, Dessert Cups, Fresh Homemade Food; local delivery limited to Khanewal City and surrounding areas, ~2-hour target) alongside the existing Pakistan-wide line (Chocolates, Jewelry, and future garments/toys/handmade goods). Checkout itself must never proceed when delivery eligibility fails, and duplicate orders must be prevented.

## Decisions

### Most of the backend order pipeline already existed — the real gap was the frontend, plus one real correctness bug

`OrderService::create()` (Phase 04) already priced orders server-side, reserved inventory per line item, and the `idempotent` middleware (Phase 04) already prevented duplicate orders via an `Idempotency-Key` header. None of "Order creation," "Inventory reservation," or "Prevent duplicate orders" needed new backend work — they needed a frontend that actually calls them correctly (a stable idempotency key generated once per checkout attempt, reused across retries, replaced only after success). The real gap was **delivery eligibility**: `resolveDeliveryRule()` only ever matched `scope='global'` or `scope='product'` rules — `scope='category'` was silently ignored, and a cart with no matching rule at all defaulted to *allowed with a $0 fee* rather than rejected. Neither behavior could express "Cakes can't ship nationwide" or "local delivery only works in Khanewal."

### Delivery eligibility is now deny-by-default, checked per line item, closest-rule-wins

`OrderService::resolveDelivery()` (replacing `resolveDeliveryRule()`) requires an explicit, active, `is_deliverable=true` rule to exist for the requested delivery type — no matching rule at any scope means not deliverable, full stop (CLAUDE.md §3's deny-by-default applied to a business-critical path, not just auth). Every distinct product in the cart is checked independently against the closest applicable rule (product scope → category scope, walking from the product's own category up through its ancestors so a block on a parent category like "Cakes" also covers "Fresh Cream Cakes" → global scope), and the whole order is rejected if *any* line fails — a mixed cart can't slip a non-deliverable item through on the back of a deliverable one. This is a deliberate behavior change from Phase 04's permissive default, so every existing checkout test that relied on "no rule configured, but still succeeds" was updated to seed an explicit baseline rule (`OrderTest::ensureDefaultLocalDeliveryRule()`) — the old behavior was never a requirement, just an untested default that the business rules in this phase made incorrect.

### The Khanewal zone is `delivery_rules` data, not a hardcoded city check

Two additive, nullable columns — `local_areas` (JSON array of city/area names) and `estimated_minutes` — extend the existing `delivery_rules` table rather than introducing a new geography concept. A `local`-type rule with `local_areas` set only matches when the order's shipping address's `city` or `area` (case-insensitive) is in that list; a rule with `local_areas` null applies everywhere, which is exactly what the nationwide rule and any category override need. `DeliveryRuleSeeder` seeds the Khanewal zone (plus a few named surrounding towns) as the global `local` rule, a permissive global `nationwide` rule, and a `nationwide: is_deliverable=false` block on each fresh category — satisfying "delivery rules must come from backend configuration, not AI prompts" as literally as possible: it's rows in a table an admin can edit.

### A new admin page, because the existing one could never reach these rules

The Category Manager's delivery-rules section (Phase 06) only ever creates rules scoped to the category being viewed — there was no admin surface for `scope='global'` at all. Rather than bend that component to a second purpose, `/admin/delivery-rules` is a new page listing every rule regardless of scope, with a scope picker (global/category) and the new `local_areas`/`estimated_minutes` fields — this is what actually makes the Khanewal zone and its fee/ETA admin-editable, not just seeded once.

### Cart is client-only; checkout re-verifies everything the client claims

There is no `carts` table (Phase 02 schema) and none was added — a `CartProvider` (`frontend/src/lib/cart.tsx`) holds cart state in `localStorage`, keyed by variant id, carrying just enough denormalized data (name, price-at-add, image) to render without extra fetches. Nothing from the cart is trusted at checkout: `OrderService::priceLines()` re-resolves the real price from the variant id, and the shipping address is now loaded and ownership-checked server-side (`Address::where('id', ...)->where('customer_id', $customer->id)`) rather than trusted from the request — the previous code accepted `shipping_address_id` with only an `exists:addresses,id` rule, which never verified the address belonged to the requesting customer. The order's `shipping_address_snapshot` is now built from that verified address server-side too, replacing a dead branch that trusted a client-supplied snapshot the Form Request never actually validated.

### A delivery-eligibility preview endpoint, so checkout can say "no" before the customer submits

"Do not allow checkout when delivery eligibility fails" is satisfied at the database/service layer regardless, but a customer shouldn't have to submit a doomed order to find that out. `OrderService::previewDelivery()` extracts the same eligibility/fee/ETA resolution `create()` uses into a side-effect-free method (no reservation, no order row), exposed at `POST /orders/delivery-eligibility`. The checkout page calls it (debounced) whenever the address or delivery type changes and disables "Place order" until a fresh, eligible result comes back — the backend rule is still what actually blocks a bad order; this is the same UX-vs-enforcement split CLAUDE.md §8 already draws for permissions ("a hidden UI button is not a security control") applied to delivery eligibility instead.

### Customer auth is a parallel, non-redirecting provider — unlike the admin panel's

`AdminAuthProvider` (Phase 06) redirects away from `/admin/*` for anyone without staff permissions, because every admin page requires one. Most of the storefront needs no login at all, so `CustomerAuthProvider` just exposes `{ user, loading }` everywhere (the header reads it to show "Login" vs "My Account") without redirecting on its own; only `RequireCustomerAuth` (used by `/checkout`, `/account/orders`, `/account/addresses`) redirects a logged-out visitor to `/account/login?redirect=...`. Login/register/logout reuse the existing JWT+refresh+CSRF session (Phase 03) and the existing `adminFetch` one-shot refresh-retry helper — there's nothing admin-specific about it despite the file path, and duplicating it for a "customer" version would just be the same logic twice.

### Order status timeline and delivery tracking are two different things, on purpose

`order_status_histories` (fulfillment lifecycle: pending → confirmed → processing → dispatched → delivered) already existed and needed no change. "Order tracking" — courier, tracking number, in-transit events — is a separate concept the `deliveries`/`delivery_tracking_events` tables already modeled (Phase 04), but a customer had no way to see their own order's delivery record at all (`GET /deliveries` requires a staff `deliveries.*` permission, and `DeliveryPolicy::view` already permitted the owning customer but there was no way to *discover* the delivery's id to reach it). `OrderController::show()` now eager-loads `delivery.trackingEvents` and `OrderResource` includes it (`null` if no delivery has been created yet) — reusing the existing, already-correct policy rather than adding a new route.

## Consequences

- Backend: one migration (`local_areas`/`estimated_minutes` on `delivery_rules`, `customization_note` on `order_items`, `estimated_delivery_minutes` on `orders`), `OrderService`'s delivery resolution rewritten, one new authenticated-customer endpoint (`POST /orders/delivery-eligibility`), `CategorySeeder` extended with Pastries/Fresh Homemade Food, a new `DeliveryRuleSeeder`. 18 new backend tests (14 in `OrderTest`, 4 in `DeliveryRuleTest`), plus one existing `CategoryTest` assertion updated for the two new categories — 206 backend tests total. This session's sandbox still has no PHP 8.4+ runtime (see ADR 0007) — these tests were written and manually traced against Laravel/Eloquent semantics but not executed here; run `php artisan test` on PHP 8.4+ to confirm them.
- Frontend: a client-only cart (`lib/cart.tsx`), a customer auth provider/gate parallel to the admin one, full checkout with live eligibility preview, order confirmation/history/detail/tracking pages, an address book, and a new admin delivery-rules page. 11 new frontend tests (9 covering cart behavior, 2 covering the auth-gate redirect), all executed and passing (62 total), plus `typecheck`/`lint`/`build` green and manual browser verification of the cart → checkout → login redirect chain against a stopped backend (full checkout submission couldn't be exercised end-to-end in this session for the same PHP-runtime reason).
- Deliberately out of scope: online payment (COD remains the only `payment_method`, unchanged from Phase 04), a dedicated product-picker UI for delivery-rule targeting (the new admin page's category `<select>` is sufficient), and real-time delivery tracking (the tracking view is pull-based, refreshed on page load, not a live feed).
