# ADR 0014: Analytics, Audit Logging & AI Cost Governance

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 14 asked for operational analytics (sales, orders, product performance, best sellers, customer metrics, COD success rate, failed delivery rate, inventory analytics, payment analytics), a complete audit-logging picture (admin actions, payment events, order changes, inventory changes, security events, AI tool calls, agent actions — with a hard rule against ever logging passwords/API keys/OTPs/payment credentials/secrets), AI cost monitoring (requests, tokens, estimated cost, model usage, agent usage) with configurable usage limits, and — cutting across all of it — deterministic backend processing preferred over AI. Most of this had partial groundwork already: `AnalyticsController` had three endpoints (`overview`, `sales`, `ai-usage`); `AuditLogger` and `audit_logs` already covered admin/payment/order/inventory actions consistently; `ai_usage_logs` already logged every chatbot reply and every Phase 13 agent tool call, with a cost estimate and one narrow per-conversation rate limit. What was genuinely missing: eight analytics categories, a code-level backstop against ever persisting a secret through the audit log, durable logging of security anomalies specifically, any usage cap at all on the agent tool-call surface, and per-model/per-agent-type visibility into AI cost despite the underlying columns already being populated.

## Decisions

### Eight new analytics methods crossed the controller's own stated threshold for extracting a service

`AnalyticsController`'s original docblock committed to "no separate analytics store/pipeline... a dedicated reporting service becomes worth it only once a concrete need... shows up." Eleven aggregation methods (the original three plus eight new: orders, product performance, best sellers, customers, COD, deliveries, inventory, payments) inline in a controller would have buried the actual HTTP concerns under query logic — that was the concrete need. `AnalyticsService` now holds every aggregation; `AnalyticsController` is a thin request-parsing/response-shaping layer over it. No new tables or migrations were needed — every method queries data that already exists.

### COD success rate and failed delivery rate are computed over *resolved* records only

An `awaiting_delivery` COD record or an `out_for_delivery`/`in_transit` delivery hasn't succeeded or failed yet — including it in either denominator would make an early cohort with many pending deliveries read as a misleadingly low success rate. `codPerformance()`/`deliveryPerformance()` both compute their rate as `resolved-success / (resolved-success + resolved-failure)`, returning `null` (not `0`) when nothing has resolved yet, so the frontend can distinguish "0% success" from "no data to judge yet."

### Permission gating moved from a repeated inline check to one route-group middleware

Every one of the original three `AnalyticsController` methods did its own `abort_unless($request->user()->hasAnyPermission(['analytics.view']), 403)`. Adding eight more methods the same way would have been eight more copies of the identical check — CLAUDE.md §8's "Role checks are centralized... not scattered ad hoc" directly named this pattern. `routes/api/analytics.php`'s route group now carries `permission:analytics.view` once; every method lost its inline check. Externally identical (confirmed by the pre-existing `GovernanceTest::test_analytics_overview_requires_analytics_view_permission` passing unchanged, plus a new test asserting the same for all eleven routes).

### Audit-log redaction is a code-level backstop, not a restatement of "the models don't have those columns"

`AuditLogger::log()` previously trusted that no audited model's `toArray()` would ever contain a password/API key/OTP/card number — true today only because `payments`/`payment_transactions` have their own dedicated schema test asserting those columns can't exist. That's an implicit guarantee that breaks silently the moment someone adds a field without thinking about CLAUDE.md's "never log" list. `AuditLogger::redact()` now recursively strips any key matching a fixed denylist (`password`, `api_key`, `otp`, `pin`, `cvv`, `card_number`, `two_factor_secret`, and more, case-insensitive, at any nesting depth) from every `before`/`after` snapshot before it's written. It's provably inert today (nothing currently audited carries these fields) and provably load-bearing the day something does.

### Security events get a durable audit-log entry, not just an application-log line

`PromptInjectionGuard::scanInbound()` already logged a flagged message via `Log::warning()` — ephemeral, unstructured, and invisible to a `super_admin` reviewing the audit trail rather than grepping server logs. It now additionally writes a `security.prompt_injection_detected` row to `audit_logs` (a bounded excerpt, not the full message, and already passing through the new redaction backstop). Auth events (login success/failure, logout, registration, CLI role assignment) already flowed into `audit_logs` since Phase 03 and needed no change. AI tool calls and agent actions are deliberately *not* duplicated into `audit_logs` as a third log — they already have two purpose-built homes (`ai_usage_logs` for every call regardless of outcome, `audit_logs` for every human approval/rejection decision, per Phase 13) and adding a third would fragment the same information rather than complete it.

### `AiUsageLimiter` generalizes a chat-only check into a service both AI-touching surfaces share

`AiChatService::aiCallBudgetExceeded()` was a private method, chat-specific, checking one thing (per-conversation-per-hour paid-call count). Meanwhile `AgentToolGateway::invoke()` — the entire Phase 13 tool-call surface — had *no* usage limit at all: an allow-listed but low-risk tool like `check_product_availability` could be called without bound by a single agent identity. `AiUsageLimiter` moves the original check (unchanged behavior) into a shared service and adds three more: a per-agent-identity hourly cap on tool calls, and two global daily caps (cost and request-count) spanning every provider and purpose. The two daily caps default to `0` ("disabled") — consistent with no live Anthropic key existing in any environment yet, a hard ceiling would be dead weight until real spend exists to cap. `AgentToolGateway::invoke()` checks the limiter first, before the registry lookup even runs, refusing and logging exactly like an unknown tool or a validation failure would — the same "always logged, whether successful or refused" guarantee Phase 13 established, now covering a fourth refusal reason.

### AI cost monitoring gained the breakdowns its own columns already supported

`ai_usage_logs.model` and `.purpose` were populated on every row since Phase 12/13 but never aggregated — `GET /analytics/ai-usage` only ever grouped by `provider` and `status`. It now also groups by `model`, by `purpose` (distinguishing chat replies from agent tool calls), and by `agent_type` (joined through `users.agent_type`, scoped to `purpose='agent_tool_call'` rows), plus token totals and a `limits` block showing every `AiUsageLimiter` cap next to today's actual usage against it. Same endpoint, same permission gate, additive fields only — nothing existing was removed or renamed, confirmed by the pre-existing `AiUsageAnalyticsTest` assertions passing unchanged.

### Tests were executed for the first time in this project's history — and found a real, unrelated bug

Every phase through Phase 13 documented its tests as "written and manually traced but not executed" because the sandbox had only PHP 8.1 while the resolved Composer lock requires 8.4.1+. Phase 14 installed PHP 8.4 via `winget` (alongside the existing PHP 8.1, no PATH conflict) specifically to close this gap, since "run tests" was an explicit, literal instruction this phase and a syntax check is not a test run. Running 13 phases' worth of never-executed tests for the first time surfaced 19 failures. One — `AgentEventLog` (Phase 13) silently failing to persist on every domain event because the model didn't know its timestamp column is `occurred_at`, not Eloquent's default `created_at` — was fixed as part of this phase, because it directly breaks the agent-approval/event-architecture behavior this phase's own audit-logging narrative depends on being real. The other 18 are genuine pre-existing bugs in Phases 04/07/08/10/12, unrelated to analytics/audit/AI-cost governance; they were left unfixed as out of this phase's scope rather than either silently ignored or used to justify an unbounded fix-everything expansion of the phase. See the README's Testing Strategy section for the itemized list.

## Consequences

- Backend: no new migrations or tables — every analytics method queries existing data. New: `app/Services/Analytics/AnalyticsService.php`; `app/Services/Ai/AiUsageLimiter.php`; `AuditLogger::redact()`; a `security.prompt_injection_detected` audit call site in `PromptInjectionGuard`; eight new routes plus a centralized `permission:analytics.view` group middleware in `routes/api/analytics.php`; three new config keys under `services.anthropic.*` (`max_agent_tool_calls_per_hour`, `daily_cost_limit_usd`, `daily_request_limit`). One pre-existing bug fixed (`AgentEventLog::CREATED_AT`). 18 new backend tests, actually executed (not just traced): 359 total, 340 passing. The 19 failures (1 fixed, 18 pre-existing and out of scope) are itemized in the README.
- Frontend: `lib/api/admin/analytics.ts` extended with eight new typed API functions and the extended `AiUsageOverview` shape; `/admin/ai-usage` extended with a model/agent-type breakdown and a limits-vs-actual-usage display; a new `/admin/analytics` dashboard page covering the eight new categories; a new `analytics` entry in `ADMIN_MODULES`. `typecheck`/`lint`/`test` (63, unchanged)/`build` all pass; manually verified in a browser with no live backend running that `/admin/analytics` redirects to `/login` without a session, no console errors beyond the expected fetch failures.
- Deliberately out of scope: fixing any of the 18 pre-existing test failures this phase's real test execution surfaced (flagged for a dedicated follow-up); a fourth audit-log destination for AI tool calls/agent actions beyond the two that already exist; DB-backed (as opposed to env-config-backed) usage limits, which would need its own review given every other AI-related setting in this codebase is env-driven; live Anthropic spend — no API key exists in any environment yet, so every cost figure here remains an estimate against zero real traffic.
