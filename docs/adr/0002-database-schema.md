# ADR 0002: Database Schema

**Status:** Accepted
**Date:** 2026-08-22

## Context

Phase 02 required a normalized PostgreSQL schema supporting the full entity list requested for the project: identity/RBAC, catalog with hierarchical categories, inventory, orders, payments, COD, delivery, marketing/content, chat/AI logging, and governance (audit logs, settings) — 35 tables in total, defined as Laravel migrations with a matching Eloquent model per table. See the [README's Database section](../../README.md#database) for the full table inventory.

## Decisions

- **Order status, payment status, and COD status are three separate columns on three separate tables** (`orders.status`, `payments.status`, `cod_records.status`), not one shared status field. This was an explicit requirement — COD needed "its own controlled payment state," and order/payment status needed to stay independently trackable so that, for example, marking an order dispatched never implicitly changes a payment's state.
- **Categories are self-referencing** (`categories.parent_id → categories.id`) to support arbitrary-depth hierarchy. Deleting a parent nulls its children's `parent_id` (promoting them to top-level) rather than cascading — a whole-subtree cascade delete was judged too destructive for a content-management-style table an admin will edit directly.
- **Products belong to categories two ways**: a nullable `products.category_id` for the canonical/breadcrumb category, plus a `category_product` many-to-many pivot for future-proof multi-category tagging. This satisfies the "future-proof" requirement without forcing every product lookup through a pivot join when only the canonical category is needed.
- **Delivery rules are scoped `global`/`category`/`product`** via a `scope` enum plus nullable `category_id`/`product_id` columns on `delivery_rules`, with a `priority` column to resolve overlaps (e.g. a product-specific rule overriding its category's rule). The invariant "scope must match which target column is set" is enforced in `DeliveryRule::booted()`, not a database CHECK constraint — see the portability decision below.
- **Every price-bearing entity lives at the variant level.** `products` has no price column; `product_variants` does. A simple product still gets exactly one (default) variant, so there's a single pricing/SKU source of truth rather than two.
- **Inventory does not store a `quantity_reserved` column.** `inventory_reservations` is the sole source of truth for reserved stock; available quantity is always computed as `quantity_on_hand − SUM(active reservations)` at query time, so the two numbers can't drift out of sync.
- **Order line items snapshot their product/variant name, SKU, and price** (`order_items.product_name`, `.sku`, `.unit_price`) in addition to nullable FKs. A historical order must stay legible even after the product it referenced is edited or deleted.
- **Orders snapshot their shipping/billing address as JSON** (`orders.shipping_address_snapshot`) in addition to a nullable `shipping_address_id` FK, for the same reason — a customer editing their saved address later must not silently rewrite the history of a past order.
- **Soft deletes are applied selectively**, per [CLAUDE.md §22](../../CLAUDE.md#22-postgresql-database-architecture)'s "decide per entity type" guidance: enabled on entities where recoverability/audit matters (`users`, `customers`, `addresses`, `categories`, `products`, `product_variants`, `orders`, `payments`, `deliveries`, `coupons`, `reviews`, `hero_banners`, `homepage_sections`, `delivery_rules`) and omitted both on append-only tables that are never edited or deleted by the application (`audit_logs`, `order_status_histories`, `payment_transactions`, `delivery_tracking_events`, `chat_messages`, `ai_usage_logs`) and on small reference/lookup tables where a hard delete is the only meaningful operation (`themes`, `system_settings`).
- **A handful of structural invariants are enforced at the Eloquent model layer instead of a database CHECK constraint or a partial unique index**: `DeliveryRule`'s scope/target consistency, and `Theme`'s "only one active theme at a time" rule. Both are portable, DB-agnostic checks written in PHP; the alternative (raw, driver-specific SQL for partial indexes/CHECK constraints) would work differently — or not at all — between the Postgres runtime and the SQLite database the test suite runs against, undermining [CLAUDE.md §22](../../CLAUDE.md#22-postgresql-database-architecture)'s provider-replaceability requirement. Every other constraint (foreign keys, standard unique indexes, `enum` columns, `NOT NULL`) is a real database constraint enforced by Laravel's schema builder identically across drivers.
- **JSON columns use Laravel's `json` type, not Postgres's `jsonb`.** Laravel's schema builder maps `$table->json()` to the `json` native type on Postgres and to `TEXT` on SQLite — both work, keeping the test suite honest against the same schema shape the production database uses. `jsonb` (with its GIN-indexing benefits) can be introduced per-column later via a Postgres-specific migration if a specific column needs indexed JSON queries; nothing here needs that yet.
- **Polymorphic relations use an explicit morph map** (`category` → `Category`, `product` → `Product`, registered in `AppServiceProvider::boot()`), so `coupon_scopes.scopable_type` and `seo_metadata.seoable_type` store short, stable strings instead of full PHP class paths that would break if a class were renamed or namespaced differently later.

## Consequences

- 39 migrations (35 domain tables + a `users` profile-extension migration + Laravel's own `cache`/`jobs`/`notifications` tables) run cleanly, in order, against both SQLite (tests) and — pending live provisioning — PostgreSQL.
- A new `tests/Feature/Database/SchemaArchitectureTest.php` exercises the schema end to end via `RefreshDatabase` and asserts the requirements above; see the [README's schema-verification instructions](../../README.md#verifying-the-schema).
- No API endpoints or controllers exist yet — this ADR covers the data layer only. RBAC *enforcement* (as opposed to the `roles`/`permissions` tables existing) is Phase 03+ work.
- The two model-layer invariants (`DeliveryRule`, `Theme`) rely on application code running through Eloquent; a raw SQL `INSERT` bypassing the model would not be caught. This is an accepted tradeoff for portability — flagged here so it isn't rediscovered as a surprise later.
