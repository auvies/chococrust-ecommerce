# ADR 0007: Dynamic Product/Category/Homepage System

**Status:** Accepted
**Date:** 2026-08-22

## Context

Phase 07 needed the storefront's catalog and homepage to become fully dynamic and admin-configurable: a category hierarchy (Categories → Subcategories → Products) seeded with nine specific initial categories but extensible with zero code changes, a homepage supporting seven section types (hero, categories, all products, best sellers, featured products, offers, reviews) that an admin can enable/disable and reorder, best sellers computed from real sales data with an optional admin override, and product search/filtering. All of this had to build on the Phase 02 schema, Phase 04 API, and Phase 05/06 frontend without a new architectural layer.

## Decisions

### Category hierarchy needed no schema change — only data and a filtering fix

`categories.parent_id` (self-referencing, Phase 02) already supports arbitrary-depth nesting, and `CategoryController` (Phase 04) already exposes full CRUD gated by `categories.manage`. "Future categories addable without code changes" was therefore already true before this phase — the actual gap was a *seeded baseline* (a fresh database had zero categories) and a *filtering* gap: `GET /products?filter[category_id]=X` only ever matched products tagged directly into category `X`, so filtering by a parent category like "Cakes" silently excluded every product filed under "Fresh Cream Cakes." `ProductController::categoryAndDescendantIds()` now does a breadth-first walk of `parent_id` to resolve a category and all of its descendants (any depth) before filtering, so "Categories → Subcategories → Products" is a real, browsable hierarchy rather than just a display tree. `CategorySeeder` seeds exactly the nine categories in the brief (Cakes as parent of Fresh Cream Cakes/Dry Cakes/Customized Cakes; Chocolates, Dessert Cups, Pizza, Jewelry, Gifts as top-level) via `firstOrCreate` keyed on slug — safe to run in every environment, and it will never overwrite a name/description an admin later edits through the Category Manager (Phase 06), since `firstOrCreate` only fills a gap, never updates an existing row.

### Best sellers: real sales data, with a deliberately reused override mechanism

Phase 05 ranked "Best Sellers" by review count because no sales data existed to rank against. It does now: `order_items` (Phase 02) has been populated by real checkouts since Phase 04's `OrderService`. `ProductController::bestSellers()` (`GET /products/best-sellers`, public) sums `quantity` per `product_id` across every order *except* `cancelled`/`refunded` ones, ranks descending, and falls back to featured products and then newest-active products if there's no sales data yet (a fresh store should never show an empty section). The "optional admin override" requirement didn't need a new table or endpoint: it reuses the existing `homepage_sections` row of type `best_sellers` and its already-freeform `config` JSON column (Phase 04/06) — an admin sets `config.product_ids` through the Homepage Manager UI that already existed, and `bestSellers()` checks for that override before computing anything. One reused mechanism instead of a second admin surface for the same concept.

### The homepage is now composed from `homepage_sections`, not a fixed component order

`HomepageSectionController` (full CRUD, `content.manage`-gated) has existed since Phase 04/06, but the Phase 05 homepage (`(storefront)/page.tsx`) never actually read it — sections were hardcoded in a fixed order. That's the core of "admin must be able to enable/disable and reorder homepage sections": the page now fetches `GET /homepage-sections` (already filtered to `is_active` for public callers) and renders a `type → component` mapping in `sort_order`, filtering `is_active` again on the frontend as defense-in-depth. `HomepageSectionSeeder` seeds the seven required types in a sensible default order via `firstOrCreate` keyed on `type` (same non-destructive contract as `CategorySeeder`), so a fresh install isn't blank. If the sections fetch fails outright or somehow still returns nothing, the page falls back to a hardcoded `DEFAULT_SECTIONS` array mirroring the seeder's own default order — CLAUDE.md §16's "failures in non-critical paths degrade gracefully" applied to the entire homepage layout, not just individual sections. A previously-missing "All Products" section (the brief's #3, never built in Phase 05) is now one of the seven, listing the newest active products with a "View all" link to `/search`.

### `/search` becomes the general catalog browse/filter surface, not just a query box

Product search/filtering needed a category (including subcategories, via the same hierarchy walk used above) and a price range, in addition to the existing text search. Rather than add a second browse page, `/search` was generalized: with no `q` at all it now lists every active product (paginated) instead of prompting "enter a search term" — this is exactly what the new "All Products" homepage section links out to. Price lives on `product_variants`, not `products`, so `min_price`/`max_price` couldn't be a plain `ApiQuery` column filter; `ProductController::index()` applies them as a `whereHas('variants', ...)` range check before handing off to `ApiQuery` for pagination/sort/search. `ListControls` gained an optional `categories`/price-range UI, gated behind an optional prop so the single-category page's product list (which doesn't need a category picker) is unaffected.

## Consequences

- Backend: `CategorySeeder`, `HomepageSectionSeeder` (both wired into `DatabaseSeeder`), `ProductController::bestSellers()` plus category-hierarchy and price-range filtering in `index()`, one new public route (`GET /products/best-sellers`). 11 new backend tests (category hierarchy + seeder idempotency, product category/price filtering, best-sellers ranking/exclusion/override/fallback, homepage section seeder idempotency) — 188 total. This session's sandbox has no PHP 8.4+ runtime available (the resolved Composer lock requires 8.4.1+; only PHP 8.1 was installed), so these new tests were written and manually traced against Laravel/Eloquent query semantics rather than executed here — including catching and fixing a real bug this way (`Builder::pluck()` rewrites the `SELECT` clause and would have dropped the `total_quantity` alias `ORDER BY` depends on; fixed by pluck-ing the materialized `Collection` instead).
- Frontend: `(storefront)/page.tsx` rearchitected to be section-driven; `/search` generalized into a browse+filter page; `ListControls` gained optional category/price-range controls; `lib/homepage.ts`'s best-sellers logic now calls the real endpoint instead of the review-count proxy. 4 new frontend tests (51 total) plus `typecheck`/`lint`/`test`/`build` all passing, and manually verified in a browser against a stopped backend: the homepage correctly falls back to `DEFAULT_SECTIONS` and every section's empty state, and `/search`'s price-filter form correctly builds `?min_price=500` on submit.
- Deliberately out of scope: a dedicated product-picker UI for the best-sellers override (the existing raw-JSON `config` field in the Homepage Manager already supports `product_ids` — a nicer picker is a UX polish item, not a functional gap); cart/checkout and the AI chatbot widget, unchanged from prior phases.
