# ADR 0013: Future AI-Agent Architecture

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 13 asked for the controlled tool/API layer eight future named agents (Sales, Customer Support, Order, Payment, Inventory, Marketing, Dispatch, Analytics) will eventually use - explicitly *not* the agents themselves ("Do not build unnecessary AI agents now. Only create the architecture and safe interfaces"). The required pipeline (`Agent → Approved Tool → Validation → Authorization → Business Logic → Database`), strict tool schemas, human approval for named high-risk operations (refund, payment verification, large discount, price changes, bulk deletion, order cancellation, dispatch cancellation), and an event architecture for 9 named lifecycle events are all real, working requirements even though no agent is actually deployed yet. A narrow allow-listed tool surface (`AiToolService`, two read-only tools) already existed from Phase 04/09/10/12 for the customer chatbot's own tool needs - the real work was generalizing that into the multi-agent framework the business described, without pretending any of the 8 agents exist.

## Decisions

### One gateway, not eight - `AiToolService` retired, `AgentToolGateway` generalizes it

Rather than build a second, parallel tool-invocation system alongside the existing one, `AgentToolGateway` *is* the generalized successor: `AiToolController` (still `POST /ai/tools/invoke`, still gated by `permission:ai.tools.use` and `throttle:ai-tools`, both unchanged) now calls it instead of the old service. The two pre-existing tools (`check_product_availability`, `get_order_status`) became `CheckProductAvailabilityTool`/`GetOrderStatusTool` classes with an empty `allowedAgentTypes()` (unrestricted) - every one of the 5 pre-existing `AiToolTest` tests passes unchanged, because the endpoint's contract never moved, only what's behind it.

### `users.agent_type` is the authorization key, not eight new roles

Provisioning eight new RBAC roles (`sales_agent`, `order_agent`, ...) would mean eight new rows in a permissions table with almost identical shape (`ai.tools.use` plus nothing else), and CLAUDE.md §8's own "AI agents must NOT be normal administrators" already treats `ai_agent` as one structural identity kind, not a family. A new nullable `users.agent_type` column (plain string, not a DB enum - the `payments.method` precedent again, since the named list is expected to grow) scopes *which tools* an already-`ai_agent`-typed identity may call, via each tool's own `allowedAgentTypes()`. `php artisan agent:provision {email} {agent_type}` (CLI-only, same trust boundary as `role:assign`) is the only way to set it - naming this command doesn't mean any agent has been provisioned; it's the mechanism for when one is.

### Strict schemas are per-tool, not a generic JSON-schema layer

Each `AgentToolInterface` implementation declares `rules(): array` - plain Laravel validation rules, the same mechanism every Form Request in this codebase already uses. `AgentToolGateway::invoke()` validates before authorization's `allowedAgentTypes()` check would even matter and *before* anything resembling business logic runs, logging a schema failure as `refused` in `ai_usage_logs` just like an unknown-tool or wrong-agent-type refusal - CLAUDE.md §9's "logged... whether successful or refused" now covers a genuinely bad request too, not just a disallowed tool name (a small, deliberate improvement over the pre-Phase-13 behavior, which never logged a validation failure at all).

### Agents cannot reach the database because tools cannot either - by construction, not by convention

`AgentToolInterface::handle()`'s only contractual obligation is "call an existing Service class or a narrowly-scoped, already-vetted read query" - every concrete tool in this phase does exactly that (`InventoryService::availableQuantity()`, `OrderService::cancel()`, `PaymentService::refund()`, or a bounded `Eloquent::where()` read). There is no tool that accepts a free-form query string, table name, or column name from agent input and no code path from an agent identity to raw SQL or an unscoped Eloquent query. `GetRecentEventsTool` makes this concrete for observability specifically: an agent asking "what happened recently" reads the compact `agent_event_logs` feed, never `orders`/`payments`/`deliveries` directly.

### High-risk tools never execute from a tool call - they execute from a human's approval, atomically

`RequestRefundTool` and `RequestOrderCancellationTool` (two of the seven named high-risk categories, chosen to prove the mechanism end-to-end without building a tool per category - the remaining five - payment verification, large discount, price changes, bulk deletion, dispatch cancellation - are classified as high-risk in the business's own vocabulary but have no tool yet, matching "only create the architecture and safe interfaces") declare `isHighRisk(): true`. `AgentToolGateway` routes any such call into `AgentApprovalService::create()` instead of ever calling `handle()` - a pending `agent_pending_actions` row is the only thing that exists at request time; the underlying `PaymentService`/`OrderService` call happens later, only from `AgentApprovalService::approve()`, only once a human reviewer acts. Approving and executing are the same atomic step deliberately - an intermediate "approved but not yet executed" state would just be a second window for the underlying data to drift with no corresponding benefit.

### Approving requires the same permission the action itself would - not one blanket reviewer role

A new `agent_actions.manage` permission (granted to `manager`/`super_admin`, matching the "manager-and-above oversight" precedent `staff.manage`/`audit.view` already set) gates *visibility* into the pending queue. But approving/rejecting additionally requires `AgentToolInterface::requiredApprovalPermission()` - `orders.refund` for a refund request, `orders.manage` for a cancellation request - the identical permission a human would need to perform that action directly. A reviewer who can see the queue but lacks the specific domain permission is refused with a 403, not silently allowed through a generic "can approve agent stuff" gate. `$reviewer` becomes `handle()`'s `$actor`, so the resulting `PaymentService`/`OrderService` audit trail names the accountable human, not "the AI."

### Event architecture: 9 named events, one listener, a durable feed - nothing reacts to them yet

Each of `ORDER_CREATED`/`PAYMENT_SUBMITTED`/`PAYMENT_VERIFIED`/`ORDER_CONFIRMED`/`ORDER_READY`/`ORDER_DISPATCHED`/`ORDER_DELIVERED`/`ORDER_CANCELLED`/`REFUND_COMPLETED` is a small `DomainEvent` subclass carrying only scalar identifiers (order/payment id, order number, a couple of business fields) - never a serialized Eloquent model, the same "optimize for low AI token usage" principle Phase 12's chatbot context-bounding already established, applied here to what a future agent would eventually read. Every event dispatches from the exact point in `OrderService`/`OrderController`/`PaymentService` where that transition already happens - no new business logic, just making existing transitions observable. `LogAgentEvent` is the *only* subscriber (registered for all 9 in `AppServiceProvider::boot()`), and all it does is write a compact row to `agent_event_logs` - deliberately the only reaction that exists right now, since building a listener that actually *does* something on these events (auto-assign a dispatch agent on `ORDER_READY`, alert an analytics agent on `ORDER_DELIVERED`, ...) would be building an agent, not architecture.

## Consequences

- Backend: three migrations (`users.agent_type`; `agent_pending_actions`; `agent_event_logs`); `AiToolService` deleted, replaced by `AgentToolGateway`/`AgentToolRegistry`/`AgentApprovalService` under `app/Services/Agents/`; six tool classes (two ported, four new); nine `DomainEvent` subclasses under `app/Events/`; one listener; a new `agent_actions.manage` permission; a new `agent:provision` CLI command; `AgentPendingActionController` (`GET /agent-actions`, `POST /agent-actions/{id}/approve`, `/reject`). 25 new backend tests (325 total) - written and manually traced but not executed for the same PHP 8.1-only sandbox reason as every prior phase, confirmed via `php -l` instead. Two real bugs were caught by manual review before they'd have shipped (see below).
- Frontend: a new `/admin/agent-actions` review screen (filter tabs by status, approve/reject with a required rejection reason). `typecheck`/`lint`/`test` (63, unchanged)/`build` all pass; manually verified in a browser that the page renders and redirects to `/login` without a live session.
- Deliberately out of scope: any of the 8 named agents actually existing, being provisioned, or doing anything autonomously; tools for the remaining five high-risk categories (payment verification, large discount, price changes, bulk deletion, dispatch cancellation); any listener that reacts to the 9 events beyond logging them; model-driven tool-calling from anywhere (the chatbot still does none, per ADR 0012, and nothing in this phase changes that).

### Two real bugs caught by manual code review, not a test run

`AgentApprovalService::approve()`'s first draft wrapped the whole method in `DB::transaction()`, including the `catch` block that records a failure as `status='failed'`. Since a caught exception still causes Laravel to roll back the transaction it was thrown inside, that "record the failure" write would itself have been silently discarded on every single approval failure - the exact case the whole `try`/`catch` existed to make durable. Caught by tracing what happens to writes made *inside* a catch block that's still lexically inside the transaction closure it's catching from; fixed by removing the outer transaction entirely (the underlying `PaymentService`/`OrderService` calls already manage their own transactional integrity, so nothing was lost by not wrapping them again).

Separately, the low-risk execution path in `AgentToolGateway::invoke()` had no `try`/`catch` around `$tool->handle()` at all - an unexpected failure (a business-rule exception, or a race where a referenced record was deleted between validation and execution) would propagate with no `ai_usage_logs` row ever written, silently defeating CLAUDE.md §9's "log every call, successful or refused" for exactly the calls most worth auditing. Fixed by catching, logging `status='error'`, and re-throwing so the caller still sees the real failure.
