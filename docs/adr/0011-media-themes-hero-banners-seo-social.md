# ADR 0011: Media, Themes, Hero Banners, SEO, and Social Preparation

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 11 asked for secure image upload (with product/hero/category media as its three concrete uses), at least 10 storefront themes with a structured, editable config, a fuller hero-banner lifecycle (upload/replace/delete-archive/reorder/desktop-mobile/CTA/preview), richer SEO fields (including Open Graph), and a prepared-not-built Facebook/Instagram integration whose tokens must never reach the frontend. Product media upload already existed and was already secure (CLAUDE.md §12: genuine image validation, a MIME allow-list, a size cap, UUID renaming) - the real work was extending that same posture to hero banners and category images (which only ever accepted a raw client-supplied URL string before this phase), building out themes/hero-banners/SEO into their full described feature sets, and a real, if narrow, CSRF gap this phase's own review surfaced.

## Decisions

### One upload service, three callers - never a client-supplied URL for a "secure" upload

`MediaController::store()` already did the right thing (`image`/`mimes:jpeg,png,webp`/`max:5120` validation, a UUID filename, storage via the configured disk) but had the storage logic inlined. `MediaUploadService::store()` extracts just the "take a validated `UploadedFile`, return its public URL" step - validation itself stays in each caller's own Form Request, since the allow-list/size cap is a per-context decision (a hero banner reasonably allows a larger file than a thumbnail). `CategoryController::uploadImage()` and `HeroBannerController::uploadImage()` are new, dedicated endpoints built on this service - `categories.image_url`/`hero_banners.image_url` remain plain URL columns (unchanged shape, still editable directly for an already-hosted/CDN image), but the *secure* path is now a real upload, not just typing a URL into a text field.

### Hero banners: desktop and mobile are different images, not one image scaled

`hero_banners` gained `mobile_image_url`, `alt_text`, and `cta_text` (`link_url` already existed - now paired with a labeled CTA, not just a bare link). `image_url` (desktop) had to become nullable to support a text-first creation flow (create the banner's copy, then attach its image via the upload endpoint - mirroring how product creation and product media upload were already two separate steps) - the column was NOT NULL, so this needed a drop-and-recreate migration rather than `->nullable()->change()` (still no `doctrine/dbal` in this sandbox, the same constraint ADR 0009 hit converting the status columns). `HeroBannerController` gained `show()` (a single banner, for the admin preview panel), `uploadImage()` (accepts either or both crops in one request), `reorder()` (the client sends the full desired id order; the server sets each banner's `sort_order` to its position), and `restore()` (undoing the existing soft-delete-based archive, which `destroy()` already was).

### Themes: a validated config shape, not an opaque JSON blob, seeded ten-plus times over

`Theme.config` was `required|array` with no structure - a theme could be created missing half the fields the storefront would need to render it. `StoreThemeRequest`/`UpdateThemeRequest` validate the full shape the business brief named: `background`/`surface`/`text_color`/`primary_color`/`secondary_color`, `typography.font_family`/`heading_font_family`, `font_sizes.{sm,base,lg,xl,2xl}`, `buttons.{radius,primary_bg,primary_text,secondary_bg,secondary_text}`. `ThemeSeeder` seeds twelve themes (Classic Chocolate through Forest Green) in exactly that shape - each one is simultaneously a real, distinct option and a worked example of a valid config, `firstOrCreate`-keyed on slug like every other content seeder. `ThemeController` gained `show()` (preview a theme's full config without activating it), `update()` (editing an existing theme was previously impossible - only create and activate existed), and `deactivate()` (turning the active theme off without activating another, so the storefront can fall back to its own default styling - the model's existing `booted()` hook already handles "activating one deactivates all others," but nothing previously handled "deactivate the only active one").

### SEO: Open Graph copy is its own field, not silently reused meta copy

`seo_metadata` had `og_image_url` but no `og_title`/`og_description` - a share preview's title/description silently fell back to whatever `meta_title`/`meta_description` said, with no way to write different, more casual copy for a social share card specifically. Both are now real, independently-editable columns. `slug` was deliberately *not* added to `seo_metadata`: it already lives on `products`/`categories` themselves (their own primary identifier), and duplicating it into a second table would create two sources of truth for the same value with no mechanism keeping them in sync - the "SEO slug" is just the entity's own slug, edited where the entity itself is edited.

### Facebook/Instagram: the same "prepared, not built" posture as WhatsApp and Easypaisa/JazzCash

No Meta developer app or Instagram Business account exists, so there is no OAuth flow, no posting, and no fetching - building any of that against credentials that don't exist would mean fabricating behavior with nothing real behind it. What's real: `config('services.facebook')`/`config('services.instagram')` (env-driven, server-only) and `SocialAccountController::status()`, a single `GET /social/accounts` endpoint that reports `connected: true/false` per platform (derived from whether the required env vars are populated) plus a couple of non-secret identifiers (page id, business account id) - never a token or app secret. Gated by `settings.manage` specifically, not the broader `content.manage` most storefront-content staff hold, because CLAUDE.md §6 treats "integrations/secrets management" as super_admin-only territory; `SocialAccountTest` asserts this both by role and by directly checking a configured secret string never appears in the response body, even when every credential is set.

### A real, if narrow, CSRF gap found and fixed - not left for later

Auditing `routes/api/catalog.php` while adding the category image-upload route surfaced that `/categories`, `/products`, and `/products/{id}/variants` mutations never had `csrf.cookie` applied - every other mutating module in this API does (payments, orders, customers, delivery, content, ...). Since this API is cookie-authenticated and the frontend/backend are expected to sit on different registrable domains (meaning the auth cookies may eventually need `SameSite=None`, which alone provides no CSRF protection - see `VerifyCsrfCookie`'s own docblock), this was a genuine, exploitable gap: a cross-site request could reach these routes carrying valid session cookies with no CSRF token check at all. Fixed by adding `csrf.cookie` to the route group (CLAUDE.md §2/§16: fix insecure code immediately on discovery, don't defer it). Every existing mutating test in `CategoryTest`/`ProductTest` needed a CSRF cookie/header added to keep passing - including the 403-permission tests, since CSRF verification runs as route middleware, before a Form Request's own `authorize()` check ever executes. New, dedicated tests (`test_category_mutations_are_rejected_without_a_valid_csrf_token`, `test_hero_banner_mutations_are_rejected_without_a_valid_csrf_token`) assert the protection itself, distinct from the permission tests it now runs ahead of.

## Consequences

- Backend: one shared `MediaUploadService`; a migration adding `mobile_image_url`/`alt_text`/`cta_text` to `hero_banners` (and making `image_url` nullable there) and `alt_text` to `categories`; a migration adding `og_title`/`og_description` to `seo_metadata`; `ThemeSeeder` (12 themes); new/rewritten controllers (`CategoryController::uploadImage()`, `HeroBannerController` gaining `show`/`uploadImage`/`reorder`/`restore`, `ThemeController` gaining `show`/`update`/`deactivate`, `SocialAccountController`); the `/categories`/`/products`/`/products/{id}/variants` CSRF fix. 34 new backend tests (277 total) - written and manually traced but not executed for the same PHP 8.1-only sandbox reason as every prior phase, confirmed via `php -l` instead.
- Frontend: a shared `uploadFormData()` helper (product media, category images, hero banner images all use it now); a rewritten Hero Banner Manager (upload, reorder via up/down controls, archive/restore with an archived view, a live preview panel, a text-first creation flow); a rewritten Theme Manager (structured color/typography/button fields, a live-updating preview card, edit, activate/deactivate); a category image-upload section; Open Graph fields in the shared `SeoSection`; a Social Integrations status panel in Settings; the storefront hero component now renders a real desktop/mobile responsive image pair with proper alt text and a labeled CTA button instead of a single CSS background-image. `typecheck`/`lint`/`test` (63, unchanged)/`build` all pass; manually verified in a browser that the new/changed admin pages render and redirect correctly without a live session.
- Deliberately out of scope: live Facebook/Instagram posting or OAuth (no account exists, per the "prepared, not built" decision above); a drag-and-drop reordering UI for hero banners (up/down buttons achieve the same `reorder()` endpoint without a new drag-and-drop dependency); independently editing a category/hero-banner's alt text without also re-uploading its image (the upload endpoints accept alt text alongside a file, not on their own - a small, acceptable limitation rather than a second endpoint for one field).
