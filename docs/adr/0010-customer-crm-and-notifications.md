# ADR 0010: Customer CRM and Order/Payment/Delivery Notifications

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 10 asked for customer profiles, order history, addresses, staff notes, and tags; reviews and ratings; order/payment/delivery notifications with WhatsApp and email "preparation"; notification templates; and RBAC hard enough that customer data is never exposed to an unauthorized staff role or to the AI agent. Several of these already existed in outline (`customers`, `addresses`, `reviews` with ratings, the polymorphic `notifications` table and its list endpoint - Phase 02/04/06/08), so this phase's real work was closing the gaps: a structured, multi-author note log where only a single overwritable field existed; a tagging system that didn't exist at all; an aggregated, honest average rating where only a client-computed one (over a partial page of reviews) existed; and an actual trigger → template → channel pipeline for notifications, where only the inbox endpoint existed with nothing ever writing to it.

## Decisions

### Structured notes are a new append-only table, not a replacement for the existing field

`customers.notes` (Phase 02) is a single overwritable text field, already gated to `customers.manage` in `CustomerResource` and already covered by Phase 06 tests. Overwriting it on every edit can't answer "who said what, when" - the actual shape a CRM notes feature needs. Rather than repurpose or remove a field other tests and the admin UI already depend on, `customer_notes` is a new, separate, append-only table (no `updated_at`, matching `inventory_movements`/`delivery_tracking_events` - Phase 09's own precedent for "this is a history log, not an editable record"): notes can be added, never edited or deleted. The existing field stays as a quick-glance summary; the new table is the real, timestamped, multi-author log. Both are documented as coexisting, not one superseding the other.

### Notes and tags get different RBAC defaults on purpose

Free-text staff notes can contain anything - a complaint, a payment dispute, commentary that reads badly out of context - so reading or writing them requires `customers.manage`, matching the existing single-field precedent exactly (view-only `support` staff can see a customer's profile and orders but not staff notes about them). Tags are different: a small, admin-curated, bounded vocabulary (`customer_tags` is its own reference table, not free text) that's exactly the kind of triage signal a view-only support agent benefits from ("this is a VIP, prioritize the call") without the same disclosure risk. Reading a customer's assigned tags only needs `customers.view`; assigning or removing one still needs `customers.manage`. This asymmetry is deliberate, not an oversight - CLAUDE.md §4's "never expose customer information to unauthorized users" is about matching exposure to actual sensitivity, not gating everything identically.

### Ratings needed a real aggregate, not a client-side average over whatever page loaded

Reading the storefront's `ReviewList` component closely surfaced a real, if minor, bug: `average = reviews.reduce(...) / reviews.length` was computed only over the fetched page (`per_page: 10`), silently wrong for any product with more than 10 approved reviews. `ProductController::show()` now does `loadAvg`/`loadCount` scoped to `is_approved=true` across every review, not just what happened to be fetched; `ProductResource` exposes `rating_average`/`rating_count`; the product page passes the real figure through and `ReviewList` only falls back to the old partial-page computation if the server didn't supply one at all (defensive, not the primary path).

### Notifications needed a real trigger → template → channel pipeline, not just an inbox

`GET/PATCH /notifications` (Phase 04) already let a user read and mark their own notifications read, but nothing anywhere ever wrote one - the "Order notifications, Payment notifications, Delivery notifications" brief needed real trigger points. `OrderService::create()`/`transitionStatus()`, `PaymentService::refund()`/`collectCod()`/`verifyCod()`/`markCodFailed()`/`markCodReturned()`, and `DeliveryController::updateStatus()` now each notify the order's customer on the state change they're already responsible for - not a new cross-cutting concern, just completing the side effects those methods already own. Every dispatch is wrapped in try/catch and logged on failure rather than allowed to bubble up (CLAUDE.md §16: a mail/WhatsApp/database-write failure must never roll back or block the order/payment/delivery transition it's attached to) - the same non-critical-path posture Phase 05's per-section storefront fetches already established.

### Notification templates are admin-editable content with a fixed taxonomy

"Implement notification templates" needed to mean something more concrete than a hardcoded string per Notification class. `notification_templates` (new: `key`, `channel`, `subject`, `body`, `is_active`) holds one row per (event, channel) pair - `order.placed`, `order.status_changed`, `payment.status_changed`, `delivery.status_changed`, each across `database`/`mail`/`whatsapp` (12 rows, seeded via `NotificationTemplateSeeder`'s `firstOrCreate`-on-`(key, channel)`, the same idempotent-seeding convention as `CategorySeeder`/`DeliveryRuleSeeder`). `NotificationTemplateService::render()` interpolates `{placeholder}` tokens against the data each Notification class supplies and returns `null` if no active template exists, so every Notification class has a hardcoded fallback body and a missing or deactivated template degrades to that fallback rather than sending nothing (CLAUDE.md §16 again). `NotificationTemplateController` deliberately only exposes `index`/`update` - no `store`/`destroy` - because the set of (key, channel) pairs is fixed by what each Notification class's `templateKey()` actually looks up; a template an application class never reads would just be dead content sitting in the table.

### WhatsApp is prepared, not built - the same posture as Easypaisa/JazzCash and MFA

No WhatsApp Business API account or credentials exist (CLAUDE.md §6), so `App\Notifications\Channels\WhatsAppChannel` never makes an outbound HTTP call - it logs the fully-rendered message and returns, gated behind `services.whatsapp.enabled` (defaults `false`). This is the identical shape ADR 0009 used for Easypaisa/JazzCash and ADR 0003 used for MFA: the data model, the trigger points, and the template-rendering pipeline are real and exercised end to end (`toWhatsApp()` on every Notification class, `NotificationTemplateService::render()` against seeded `whatsapp`-channel templates); only the final "call a real provider" step is a deliberate no-op pending an actual account. Wiring a real provider later means implementing `WhatsAppChannel::send()`'s body only - no Notification class, controller, or template changes. Email is further along by comparison - Laravel's `mail` channel is genuinely wired (`MAIL_MAILER=log` by default, so a `toMail()` call really renders and "sends," just to the log instead of a real inbox) - "prepared" here means safely defaulted, not stubbed out.

### AI's exclusion from customer data is now written down, not just structurally true

`AiToolService` never had a tool that touched `customers`, `addresses`, `customer_notes`, or `customer_tags` - true by omission, the same state payment/COD verification was in before ADR 0009 made it an explicit, permanent rule. The docblock now says so directly: `get_order_status`'s hardcoded `order_number`/`status`-only return shape is called out as a deliberate PII exclusion (the underlying `Order` model has contact name/phone/address; the tool's own return array never touches them), and any future tool needing order context must stay exactly that narrow. This mirrors ADR 0009's "written down, not just structurally true" reasoning for payment verification.

## Consequences

- Backend: three new tables (`customer_notes`, `customer_tags` + `customer_tag_assignments`, `notification_templates`); two new models (`CustomerNote`, `CustomerTag`) plus one (`NotificationTemplate`); a new `notifications.manage` permission (granted to `manager`/`super_admin`, matching the `content.manage`/`coupons.manage` precedent for what `manager` gets); `CustomerNoteController`/`CustomerTagController`/`NotificationTemplateController`; four new `Notification` classes (`OrderPlaced`, `OrderStatusChanged`, `PaymentStatusChanged`, `DeliveryStatusChanged`) sharing one abstract base (`CustomerFacingNotification`) for channel selection and template-then-fallback rendering; `NotificationTemplateService`; `WhatsAppChannel`; rating aggregation on `ProductController::show()`/`ProductResource`. 21 new backend tests (243 total) - written and manually traced but not executed for the same PHP 8.1-only sandbox reason as every prior phase (confirmed via `php -l` syntax checking instead, per the ADR 0009 precedent).
- Frontend: an extended customer detail page (order history, the structured notes log, tag assignment); a new Notification Templates admin page; a new customer-facing `/account/notifications` page (linked from `AccountNav`); the product page's rating display now uses the real server aggregate instead of a partial-page client computation. All four verification commands (`typecheck`/`lint`/`test`/`build`) pass; 63 frontend tests (unchanged - no new frontend unit tests were added this phase, only new pages/functions exercised via the existing build/typecheck/manual-browser verification).
- Deliberately out of scope: live WhatsApp/SMS gateway integration (no account exists, per the "prepared, not built" decision above); a general-purpose customer segmentation/marketing tool beyond tags (tags are staff triage labels, not a campaign-targeting system); editing or deleting a staff note once posted (append-only by design).
