# ADR 0012: AI Chatbot

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 12 asked for the storefront's customer-facing AI chatbot, built around an explicit cost architecture: `Customer Query → Intent Detection → Deterministic Backend Lookup where possible → Relevant Data Retrieval → AI only when necessary → Response`, with prices/stock/delivery rules/business hours/payment methods/order status/contact details handled deterministically and never sent to a model. On top of that: context limits, conversation-history limits, summarization, rate limits, response token limits, AI usage logging, cost monitoring, prompt-injection protection, a hard rule against ever revealing the system prompt/API keys/secrets/DB credentials/internal tools/admin information, and no arbitrary SQL access for the AI. `chat_conversations`/`chat_messages`/`ai_usage_logs` and a narrow, allow-listed `AiToolService` (Phase 04/09/10) already existed - what didn't exist was anything that actually generated a bot reply. `ChatController::sendMessage()` stored a customer's message and stopped there.

## Decisions

### The pipeline is real code, not a single AI call with instructions to "be careful about cost"

`AiChatService::respond()` is the literal pipeline: `ChatIntentDetector::detect()` (plain regex/keyword matching - deliberately not a model call, since classifying "which of a handful of known categories" doesn't need one, and using AI to decide whether AI is needed would defeat the entire cost architecture) → `ChatBackendLookupService::respond()` (one method per intent - price/stock/delivery/hours/payment-methods/order-status/contact, each either fully answers from real data or returns `null`, never partially) → only past that point does `retrieveRelevantContext()` (bounded, max 3 product snippets) and the AI provider get involved at all. Every branch - deterministic or AI - stores exactly one `chat_messages` row and exactly one `ai_usage_logs` row, so "how many replies were free vs. cost money" is a direct query, not something inferred after the fact.

### Deterministic lookups read real data, not hardcoded strings

`deliveryAnswer()` reads the same `delivery_rules` table `OrderService::resolveDelivery()` itself checks - an admin editing delivery rules through the admin panel changes what the chatbot says, with zero code change. `businessHoursAnswer()`/`contactAnswer()` read `system_settings` (seeded via a new `BusinessSettingsSeeder`, editable through `/admin/settings`). `paymentMethodsAnswer()` reads `config('payments.methods')`. `priceAnswer()`/`stockAnswer()` search `products` by a stopword-stripped term extracted from the message and, for stock, reuse `InventoryService::availableQuantity()` directly rather than re-deriving the on-hand/reserved math a second time.

### Order status is scoped to the asker's own orders - a stricter rule than the existing AI tool

`AiToolService::getOrderStatus()` (the `ai_agent` identity's own allow-listed tool) already answers with `status` only, no PII - but it has no concept of "whose order this is," because nothing calls it in a context where that matters yet. `ChatBackendLookupService::orderStatusAnswer()` is reached directly from a customer's own chat message, so it additionally requires the order to belong to `$conversation->customer` - a customer typing a stranger's real order number learns nothing (`ChatBotTest::test_order_status_never_reveals_another_customers_order`). If no order number is found in the message, it answers about the customer's own most recent order instead of asking the AI to guess.

### Context/history limits and summarization are both deterministic, and both real

`config('services.anthropic.max_history_messages')` (default 8) bounds how many recent turns are sent verbatim; `ChatSummarizationService::refresh()` compacts everything older into one bounded text blob (`chat_conversations.summary`, new column) instead of ever resending the full transcript. Summarization is deliberately plain string truncation/concatenation, not a second AI call - summarizing with a model would mean paying to save money, and would re-run on every new message in a long conversation. `retrieveRelevantContext()` similarly caps at 3 products with truncated descriptions - never the catalog, never a raw query result.

### Two independent rate/cost controls, not one

The HTTP-level `chat` RateLimiter (15/min per user, `AppServiceProvider`) caps request *volume* on `POST /chat/conversations/{id}/messages` regardless of whether a given message ends up costing anything. `AiChatService::aiCallBudgetExceeded()` is a separate, cost-specific circuit breaker: it reads `ai_usage_logs` directly for how many `provider='anthropic'` calls this *conversation* has triggered in the last hour, capped by `services.anthropic.max_ai_calls_per_conversation_per_hour` (default 15) - a request that would otherwise reach the model instead gets a fixed, free reply. This is deliberately read from the audit trail, not an in-memory counter, so it holds across requests/processes without new infrastructure.

### Response token limits and a real, gracefully-degrading provider

`AnthropicChatProvider::complete()` always sends `max_tokens` (config, default 400) - a hard ceiling on cost per call, enforced by the API itself. No `ANTHROPIC_API_KEY` is configured in any environment yet (same "prepared" posture as WhatsApp/Facebook/Instagram in Phase 10/11), but unlike those, the chatbot is meant to work *today* - so the provider throws immediately, before any network call, when the key is empty, and `AiChatService` catches that and returns a safe, honest fallback message. This makes the entire "AI needed but unavailable" path fully testable without live network access (`ChatBotTest::test_an_open_ended_question_falls_back_gracefully_with_no_api_key_configured`), and the "AI available and working" path is exercised too, via `Http::fake()` simulating a real Anthropic response - both branches are real, tested code, not one built and one stubbed.

### Prompt injection: structural first, pattern-matching second, output-scanning third

The structural defense (CLAUDE.md §10) is that user text is always sent as a `user`-role message in the API's own `messages` array, never string-concatenated into the system prompt - `AnthropicChatProvider` has no code path that could do the latter even by accident. On top of that, `PromptInjectionGuard::scanInbound()` pattern-matches common jailbreak/override phrasing ("ignore previous instructions," "reveal your system prompt," "you are now," ...) and - distinct from just logging it - routes the message down the deterministic-reply path instead of ever reaching the paid model, which is simultaneously a security control and a cost control. `sanitizeOutbound()` is a hard, code-enforced backstop that strips anything shaped like a real credential from a reply before it reaches the customer, regardless of what the model actually said, since model behavior is probabilistic and the system prompt's own instructions are not a guarantee. All three layers are directly tested, including a test that inspects the actual outbound HTTP request body to confirm a configured API key never appears in the prompt text, only the header.

### No tool-calling, so no expanding "what can the AI reach" surface

The chatbot's AI step is a single bounded completion per reply - it does not do model-driven function/tool-calling, and has no path to `AiToolService` or any other tool. Everything the model can talk about is either baked into the system prompt (fixed instructions) or passed as pre-fetched, bounded context (`retrieveRelevantContext()`'s product snippets). This is a deliberate scope decision, not an oversight: adding tool-calling later would need its own allow-list, its own human-in-the-loop story for anything state-changing (CLAUDE.md §9), and its own review - conflating it with this phase's "make replies exist at all" goal would have expanded the security surface without a corresponding requirement asking for it.

### Cost monitoring is a real admin screen, not just logging that nobody looks at

`AnalyticsController::aiUsage()` (new, `analytics.view`-gated, reusing the existing controller rather than a new analytics pipeline) aggregates `ai_usage_logs` into total replies, a cost total, a provider breakdown (`internal` vs `anthropic` - the deterministic/AI split CLAUDE.md's cost rule is actually about), and a status breakdown (success/error/refused). A new `/admin/ai-usage` page renders it. Deterministic replies are logged too, at `cost_usd=0` - without that, cost monitoring could only ever show AI spend in isolation, never the ratio that actually proves the architecture is working.

### A real bug caught by manual code review, not a test run - again

`respondWithAi()`'s first draft built the bounded history via `buildHistory()` (which, since the controller persists the customer's message before calling this service, already includes that message as the last entry) and then separately appended `['role' => 'user', 'content' => $text]` again - sending the customer's own message to the model twice on every single AI call. Harmless to correctness (the model would have just seen redundant context) but directly wasteful of the exact thing this phase exists to minimize - tokens, and therefore cost. Caught by tracing `buildHistory()`'s query against what `ChatController::sendMessage()` actually persists before invoking it, not by running the code (same PHP 8.1-only sandbox constraint as every prior phase). Fixed by removing the redundant append; `buildHistory()`'s own query was additionally given a secondary `orderBy('id')` (and `ChatSummarizationService::refresh()`'s matching `orderBy('id')`) so the two services agree on exactly which messages fall inside vs. outside the verbatim window even when several messages share the same `created_at` second - without that, a message could in principle end up counted as both "recent" and "summarized," or as neither.

## Consequences

- Backend: one migration (`chat_conversations.summary`); six new services under `app/Services/Ai/` (`ChatIntentDetector`, `ChatBackendLookupService`, `ChatSummarizationService`, `PromptInjectionGuard`, `AiChatService`, plus `Providers/AnthropicChatProvider`); `ChatController::sendMessage()` now returns `{message, reply}` instead of just the stored message (existing tests updated for the new shape); a new `chat` rate limiter; a new `AnalyticsController::aiUsage()` endpoint; a new `BusinessSettingsSeeder`; a new `AiUsageLogFactory`. 22 new backend tests (300 total) - written and manually traced but not executed for the same PHP 8.1-only sandbox reason as every prior phase, confirmed via `php -l` instead. Several tests use `Http::fake()` to exercise the real success path against a simulated Anthropic response, without needing live network access.
- Frontend: a new customer-facing `ChatWidget` (floating button + panel, gated behind customer login, mounted on every storefront page) and a new admin `/admin/ai-usage` cost-monitoring dashboard. `typecheck`/`lint`/`test` (63, unchanged)/`build` all pass; manually verified in a browser that the widget opens, shows the logged-out prompt correctly with no console errors beyond the expected "backend not running" fetch failures, and that `/admin/ai-usage` redirects to login without a live session.
- Deliberately out of scope: model-driven tool-calling from the chatbot (see "No tool-calling" above); AI-generated (rather than deterministic) history summarization; anonymous/guest chat (conversations still require a `Customer`, matching `ChatController::store()`'s pre-existing requirement - expanding chat to anonymous visitors is a separate, larger auth change this phase wasn't asked to make).
