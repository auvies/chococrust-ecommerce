## What Choco Crust Is

Choco Crust is a food/dessert e-commerce brand selling directly to customers online, with fulfillment via local delivery in its home city and shipping across Pakistan for shelf-stable items. The platform is a website (storefront + admin panel) backed by an API and database, with an AI chatbot for customer-facing support and, in a later phase, AI agents that help run parts of the business.

## Admin Panel

Built in Phase 06, on top of the Phase 04/05 API and Phase 03 auth layer. See [ADR 0006](docs/adr/0006-admin-panel.md) for the full reasoning; this is the short version.

**Real login, not a bolt-on.** `/login` calls `POST /v1/auth/login` directly from the browser (the same JWT+refresh+CSRF cookie session Phase 03 built) and `/admin/*` is wrapped in an `AdminAuthProvider` that calls `GET /v1/auth/me` on load — the one sanctioned way to know who's logged in and what they can do, since the JWT is httpOnly and hand-rolled and must never be decoded client-side. A session whose 15-minute access token has expired gets one silent refresh-and-retry (found and fixed during manual browser testing) rather than an unnecessary logout.

**RBAC enforced at three layers, not just hidden buttons.** (1) The sidebar only lists modules the logged-in user holds a permission for ([`src/lib/permissions.ts`](frontend/src/lib/permissions.ts) mirrors `RolePermissionSeeder` slug-for-slug). (2) Every module page is wrapped in `<RequirePermission anyOf={[...]}>`, so navigating straight to a URL you lack permission for shows "Access denied," not the real screen or a crash. (3) None of this is the actual security boundary — every mutation still goes through the backend's own permission check regardless of what the UI shows (CLAUDE.md §8's "a hidden UI button is not a security control"), verified directly: logging in as three different roles (`support`, `manager`, `super_admin`) in a browser showed exactly the module set each role's seeded permissions predict, and direct URL navigation to a forbidden module was blocked every time.

**Category Manager, the most detailed requirement, built in full:** add/edit, archive (soft-delete), parent category, subcategories (listed on the detail page), image URL, SEO (shared with Product Manager via one `SeoSection` component), sort order, active/inactive, and delivery rules (list/add/edit/delete, scoped global/category/product) — all exercised in a real browser session against a live backend.

**Four small, necessary backend additions — everything else in this phase is frontend-only.** Auditing the API before building against it surfaced four admin capabilities the Phase 04 API genuinely couldn't do yet: manage a category's delivery rules, edit a product variant's price after creation, list COD records at all, and see a cross-product review moderation queue. Each was added as a minimal, permission-gated, audit-logged endpoint following the exact conventions already established (a `DeliveryRuleController`, `ProductVariantController`, two `PaymentController` methods, and one `ReviewController` method) — not a scope expansion, just filling gaps a required admin screen couldn't function without. Covered by 19 new backend tests (158 → 177).

**No secrets exposed, direct browser-to-API calls.** Admin mutations call the Laravel API directly from the browser (`credentials: "include"` plus the CSRF double-submit header read from the non-httpOnly `cc_csrf_token` cookie — exactly what that cookie is designed for), which required setting `CORS_ALLOWED_ORIGINS=http://localhost:3000` in the backend's `.env` (documented in `.env.example` since Phase 01, just never previously exercised since the Phase 05 storefront never made an authenticated call).

Verify with `cd frontend && npm run typecheck && npm run lint && npm run test && npm run build` — all four pass, 47 tests including dedicated authorization tests (permission-matrix logic, sidebar filtering per role, `RequirePermission` allow/deny, `AdminAuthProvider` redirect-when-unauthenticated and redirect-when-zero-permissions, and the 401-refresh-retry flow). Manually verified end-to-end in a browser: login/logout for three roles, RBAC-correct sidebar and direct-URL blocking, and real mutations (category + delivery rule creation, inventory adjustment, review approval, order status transition) against a live backend.

## Public Storefront

Built in Phase 05, entirely on top of the Phase 04 API — no other backend changes were needed. See the pages, components, and API-client layers below; this is the short version.

**Pages.** Home (`/`, section-driven since Phase 07 — see below), all-categories index (`/categories`), category listing with subcategories/filter/sort/search/pagination (`/categories/[id]/[slug]`), product detail with gallery/variants/reviews/add-to-cart (`/products/[id]/[slug]`, add-to-cart since Phase 08), a general browse/filter page doubling as search results (`/search`, generalized in Phase 07 — see below), About, Contact, and FAQ. Cart, checkout, order confirmation/history/tracking, and an address book were added in Phase 08 — see [Cart, Checkout & Order Fulfillment](#cart-checkout--order-fulfillment-phase-08) below.

**Nothing is hardcoded.** Every product, category, hero banner, and review comes from the API at request time. The root layout (`src/app/layout.tsx`) sets `export const dynamic = "force-dynamic"` — the header (categories) and footer (public settings) are themselves API-driven, so the whole app renders per request rather than being statically generated against data that could go stale, and the production build never needs a live backend to succeed (verified: `next build` passes with the backend stopped).

**"Best Sellers" and "Offers" were originally derived signals, not faked.** At launch (Phase 05) the backend had no sales-count column, so "Best Sellers" ranked a pool of active products by live approved-review count — a documented proxy, not a claim of exact sales data. Phase 07 replaced that proxy with real sales-data ranking once order history existed to rank against (see [Product Catalog & Homepage](#product-catalog--homepage-phase-07) below). "Offers" still scans a product pool for variants where `compare_at_price > price` and surfaces the largest live markdowns — that signal was already genuine. Both sections, plus "Featured Products" (`is_featured=1`) and testimonials (top-rated approved reviews from that same pool), are fetched with one shared candidate pool per homepage load specifically to keep the request count low against the backend's general rate limit (CLAUDE.md §14) — this was found and fixed during manual browser verification, where the original per-section-fetch design pushed a single page load close to the 60-req/min ceiling.

**SEO-friendly, id-based routing.** The backend's product/category routes resolve by numeric id only (no slug route-key configured — confirmed by reading the controllers). Rather than pretend otherwise, product/category URLs are `/{id}/{slug}` (e.g. `/products/42/chocolate-cake`): the id is what's actually fetched, the slug is for readability and is kept in sync via a redirect if it ever goes stale. Per-page `generateMetadata` pulls the backend's `SeoMetadata` row when a content manager has set one (`GET /seo/{type}/{id}`), falling back to the entity's own name/description otherwise. `app/sitemap.ts` and `app/robots.ts` are built from live catalog data (bounded to 100 categories/products) rather than a static list.

**Mobile-first, responsive.** Tailwind's unprefixed utilities are the mobile baseline throughout (grid columns, nav collapse into a hamburger menu, stacked layouts) with `sm:`/`lg:` breakpoints layering up — verified in the browser at both mobile (375px) and desktop (1280px) viewports.

**Resilient by section, not by page.** Every data-fetching call site (`src/lib/api/*.ts`, `src/lib/homepage.ts`) catches its own errors and returns an empty/fallback value rather than throwing — a broken or slow endpoint degrades that one section to an empty state instead of taking down the whole page (CLAUDE.md §16), which was exercised directly during verification when the rate limiter above returned 429s.

**No secrets exposed.** The only client-side env vars are `NEXT_PUBLIC_API_BASE_URL` (already present from Phase 01) and the newly added `NEXT_PUBLIC_SITE_URL` (used only for canonical/OG tags and the sitemap) — both are public URLs, not secrets, matching CLAUDE.md §6.

Verify with `cd frontend && npm run typecheck && npm run lint && npm run test && npm run build` — all four pass (see [Testing Strategy](#testing-strategy) for the current total, since the shared `apiFetch` client gained credentials/CSRF coverage in Phase 06). Manually verified end-to-end in a browser against a locally seeded backend: homepage sections, product detail, category browsing with filter/sort, search, 404 handling for a nonexistent product, and the mobile viewport.

## Product Catalog & Homepage (Phase 07)

Built in Phase 07, on top of the Phase 02 schema, Phase 04 API, and Phase 05/06 frontend — no new architectural layer. See [ADR 0007](docs/adr/0007-dynamic-catalog-and-homepage.md) for the full reasoning; this is the short version.

**Category hierarchy: Categories → Subcategories → Products, seeded but not hardcoded.** `categories.parent_id` already supported arbitrary-depth nesting and full admin CRUD (`categories.manage`) since Phase 02/04 — nothing there needed to change. `CategorySeeder` (wired into `DatabaseSeeder`, safe to run in every environment) seeds the nine initial categories from the brief: **Cakes** as a parent of **Fresh Cream Cakes**, **Dry Cakes**, and **Customized Cakes**, plus **Chocolates**, **Dessert Cups**, **Pizza**, **Jewelry**, and **Gifts** as top-level categories. Every seeded row uses `firstOrCreate` keyed on slug, so re-running the seeder in production never overwrites a name/description an admin later edits through the Category Manager — it only fills a gap on a fresh database. Future categories (Handmade Garments, Kids Garments, Adult Garments, Toys, Other Handmade Products, or anything else) need **zero code changes**: they're added the same way any category is, through `/admin/categories`.

**Filtering by a parent category now actually includes its subcategories.** `GET /products?filter[category_id]=X` previously matched only products tagged directly into category `X` — filtering by "Cakes" silently excluded "Fresh Cream Cakes" products. `ProductController::categoryAndDescendantIds()` now walks `parent_id` breadth-first to resolve a category plus every descendant at any depth before filtering, so the hierarchy is real and browsable, not just a display tree.

**"Best Sellers" now ranks real sales data, with a reused override mechanism.** `GET /products/best-sellers` (public) sums `order_items.quantity` per product across every order **except** `cancelled`/`refunded` ones, ranks descending, and falls back to featured products and then newest-active products so the section is never empty on a fresh store. The brief's "optional admin override" reuses the `homepage_sections` row of type `best_sellers` and its existing freeform `config` JSON column (Phase 04/06) — an admin sets `config.product_ids` through the Homepage Manager UI that already existed, and the endpoint checks for that override before computing anything from sales data at all. No second admin surface for the same concept.

**The homepage is now composed from the database, not a fixed component order.** `HomepageSectionController` (full CRUD, `content.manage`-gated) has existed since Phase 04/06, but the Phase 05 homepage never actually read it. `(storefront)/page.tsx` now fetches `GET /homepage-sections` and renders a `type → component` map in `sort_order`, respecting `is_active` (filtered server-side for public callers, and again on the frontend as defense-in-depth) — this is the actual mechanism behind "admin must be able to enable/disable and reorder homepage sections." `HomepageSectionSeeder` seeds the seven required section types (hero, categories, all products, featured products, best sellers, offers, reviews) in a sensible default order, with the same non-destructive `firstOrCreate`-on-`type` contract as `CategorySeeder`. If the sections fetch fails entirely, the page falls back to a hardcoded `DEFAULT_SECTIONS` array mirroring the seeder's default order, so the homepage degrades gracefully (CLAUDE.md §16) rather than going blank. The previously-missing **"All Products"** section (never built in Phase 05) is now one of the seven — the newest active products, linking out to `/search`.

**`/search` is now the catalog's general browse/filter page, not just a query box.** With no `q` at all it lists every active product, paginated — exactly what the new "All Products" section's "View all" link points to. It now also supports a category filter (including subcategories, via the same hierarchy walk above) and a price range. Price lives on `product_variants`, not `products`, so `min_price`/`max_price` can't be a plain `ApiQuery` column filter — `ProductController::index()` applies them as a `whereHas('variants', ...)` range check before `ApiQuery` handles pagination/sort/search. `ListControls` gained an optional category/price-range UI, gated behind an optional prop so the single-category page's product list is unaffected.

**A real bug caught by manual code review, not a test run.** This session's sandbox has no PHP 8.4+ runtime available (the resolved Composer lock requires 8.4.1+, only PHP 8.1 was installed) — the 11 new backend tests below were written and manually traced against Laravel/Eloquent semantics but could not be executed in this environment; run them yourself with `php artisan test` on PHP 8.4+ to confirm. That manual trace caught a real bug before it could ship: the first draft of the best-sellers query used `Builder::pluck('product_id')` on a `SUM(quantity) as total_quantity` aggregate query — `pluck()` rewrites the `SELECT` clause down to just the plucked column, which would have silently dropped the `total_quantity` alias that `ORDER BY` depends on and broken the query the first time real sales data existed. Fixed by materializing with `.get()` first and plucking the in-memory `Collection` instead.

Verify backend with `cd backend && php artisan test` (PHP 8.4+ required) — 11 new tests (category hierarchy and seeder idempotency, product category/price filtering, best-sellers ranking/exclusion/override/fallback, homepage-section seeder idempotency), 188 total. Verify frontend with `cd frontend && npm run typecheck && npm run lint && npm run test && npm run build` — all four pass, 4 new tests (51 total: the homepage's default-layout-fallback and admin-configured-order rendering, and `/search`'s browse-with-no-query and filter-passthrough behavior). Manually verified in a browser against a stopped backend: the homepage correctly falls back to `DEFAULT_SECTIONS` with every section's empty state, and submitting a price filter on `/search` correctly builds `?min_price=500`.

## Cart, Checkout & Order Fulfillment (Phase 08)

Built in Phase 08, on top of the Phase 02 schema, Phase 04 order/inventory/idempotency infrastructure, and Phase 03 auth. See [ADR 0008](docs/adr/0008-cart-checkout-and-delivery-eligibility.md) for the full reasoning; this is the short version.

**Most of the backend order pipeline already existed — the real gap was delivery eligibility, plus one real security gap.** `OrderService::create()` (Phase 04) already priced orders server-side and reserved inventory per line item; the `idempotent` middleware (Phase 04) already prevented duplicate orders via an `Idempotency-Key` header. Neither needed new backend work. What did: `resolveDeliveryRule()` only ever matched `scope='global'` or `scope='product'` rules (`scope='category'` was silently ignored), defaulted to *allowed with a $0 fee* when no rule matched at all, and trusted `shipping_address_id` with only an `exists:addresses,id` check — never verifying the address belonged to the requesting customer.

**Delivery eligibility is now deny-by-default, checked per line item.** `OrderService::resolveDelivery()` requires an explicit, active, `is_deliverable=true` rule for the requested delivery type — no matching rule means not deliverable (CLAUDE.md §3's deny-by-default, applied to checkout, not just auth). Every distinct product in the cart is checked against the closest applicable rule — product scope → category scope (walking from the product's own category up through its ancestors, so a block on "Cakes" also covers "Fresh Cream Cakes") → global scope — and the whole order is rejected if any line fails, so a mixed cart can't slip a non-deliverable item through on a deliverable one's back.

**The Khanewal local-delivery zone is `delivery_rules` data, not a hardcoded city check.** Two additive columns — `local_areas` (JSON) and `estimated_minutes` — extend `delivery_rules`. A `local`-type rule with `local_areas` set only matches when the shipping address's city/area (case-insensitive) is in that list; null means no geographic restriction. `DeliveryRuleSeeder` seeds the Khanewal zone (plus a few surrounding towns) as the global `local` rule with a ~2-hour ETA, a permissive global `nationwide` rule, and a `nationwide: is_deliverable=false` block on each fresh category (**Cakes**, **Pastries**, **Pizza**, **Dessert Cups**, **Fresh Homemade Food** — the latter two newly added to `CategorySeeder`). Pakistan-wide lines (**Chocolates**, **Jewelry**, and any future garments/toys/handmade category) need no rule of their own — they simply inherit the global nationwide rule, satisfying "delivery rules must come from backend configuration, not AI prompts" and Phase 07's "future categories need zero code changes" at once. A new `/admin/delivery-rules` page makes this genuinely admin-editable: the existing Category Manager's delivery-rules section only ever creates category-scoped rules, so the global Khanewal-zone rule had no admin surface at all before this.

**Cart is client-only; checkout re-verifies everything the client claims.** There is no `carts` table — `CartProvider` (`frontend/src/lib/cart.tsx`) holds cart state in `localStorage`, keyed by variant id. Nothing from it is trusted at checkout: price is always re-resolved from the variant id, and the shipping address is now loaded and ownership-checked server-side (`Address::where('id', ...)->where('customer_id', $customer->id)`) instead of trusted from the request — closing the gap described above. The order's `shipping_address_snapshot` is now built from that verified address server-side too, replacing a dead branch that trusted a client-supplied snapshot the Form Request never actually validated. Each cart line also carries an optional free-text **customization note** (e.g. a cake message) through to a new `order_items.customization_note` column — "product customization" alongside "product variants" (size/flavor) as a distinct concept.

**A delivery-eligibility preview endpoint, so checkout can say "no" before the customer submits.** `POST /orders/delivery-eligibility` (new) exposes the same eligibility/fee/ETA resolution `create()` uses, with no reservation and no order row created. The checkout page calls it (debounced) whenever the address or delivery type changes and disables "Place order" until a fresh, eligible result comes back — "do not allow checkout when delivery eligibility fails" enforced proactively in the UI, on top of the backend rule that actually blocks a bad order regardless.

**Customer auth is a parallel, non-redirecting provider — unlike the admin panel's.** `AdminAuthProvider` (Phase 06) redirects anyone without staff permissions away from `/admin/*`, because every admin page requires one. Most of the storefront needs no login at all, so `CustomerAuthProvider` just exposes `{ user, loading }` everywhere (the header shows "Login" vs "My Account" from it) without redirecting on its own; only `RequireCustomerAuth` (wrapping `/checkout`, `/account/orders`, `/account/addresses`) redirects a logged-out visitor to `/account/login?redirect=...`. Registration (`/account/register`) reuses the existing `POST /auth/register` endpoint, which already creates the `customer` role and `Customer` profile and logs the new account in immediately (Phase 03) — no new backend auth work needed.

**Order status timeline and delivery tracking are different things, kept separate.** `order_status_histories` (pending → confirmed → processing → dispatched → delivered) already existed. "Order tracking" — courier, tracking number, in-transit events — reuses the existing `deliveries`/`delivery_tracking_events` tables and `DeliveryPolicy` (which already permitted the owning customer to view their delivery, but a customer had no way to *discover* its id, since `GET /deliveries` is staff-only). `OrderController::show()` now eager-loads `delivery.trackingEvents` and `OrderResource` includes it (`null` until a delivery exists) — no new route needed.

**A real bug caught by manual code review, not a test run.** As with Phase 07 (see below), this session's sandbox has no PHP 8.4+ runtime. Tracing the eligibility rewrite by hand caught a real issue before it shipped: the coupon/discount math and the new eligibility check both needed the customer's real `Address` model (not just an id) loaded *before* pricing — getting the load order wrong would have let an unowned address slip through on the happy path while still rejecting it on the error path, an inconsistency that's easy to miss without deliberately tracing both branches.

## Payment, COD, Inventory & Delivery (Phase 09)

Built in Phase 09, hardening four modules that already existed in outline since Phase 02/04/08 but had real gaps once traced closely. See [ADR 0009](docs/adr/0009-payment-cod-inventory-delivery.md) for the full reasoning; this is the short version.

**Payment status is now its own real vocabulary, separate from order status and COD status.** `payments.status` was a native DB enum (`pending, authorized, paid, partially_refunded, refunded, failed, cancelled`) — adding the business's requested `cod_pending`/`cod_confirmed`/`cod_collected` states would have needed a schema migration (via `doctrine/dbal`, which isn't installed in this sandbox) every time the vocabulary grows again. `orders.status` and `inventory_reservations.status` had the identical problem the moment this phase needed `ready`/`completed` order states and a `fulfilled` reservation state. All three were converted from native enums to plain indexed strings (matching the precedent `payments.method` already set — see its own migration comment), with validation moved entirely to the application layer: Form Requests bound to `config('payments.statuses')`/an explicit `in:` list, and `OrderService::TRANSITIONS` as the actual authority on which *transitions* are legal from a given status. Nothing about the three-separate-state-machines design changed — marking an order `confirmed` still never touches `payments.status` except at the one point the business flow itself implies it should (see next).

**The full COD flow (Order Created → Inventory Reserved → COD Pending → Confirmed → Processing → Ready → Dispatched → Out for Delivery → Delivered → COD Collected → Completed) is real now, mapped across all three state machines rather than forced into one.** `OrderController::store()` starts a COD order's payment at `cod_pending` (a non-COD method starts at the generic `pending`, since there's no gateway to await confirmation from yet). `OrderService::transitionStatus()` gained `ready` (prepared, awaiting dispatch) and `completed` (the whole order — delivery and payment — is settled) to its transition graph, plus three side effects triggered by the *order* status changing, each still touching only the table it's actually about: moving to `confirmed` commits the order's stock reservations and bumps a COD payment `cod_pending → cod_confirmed`; moving to `delivered` fulfills those reservations (see "Sold stock" below); moving to `cancelled` releases them and moves a still-in-flight payment to `cancelled` — never downgrading one that's already `paid`. `PaymentService::collectCod()` (the rider's own claim) now also bumps the payment to `cod_collected`, distinct from `verifyCod()` (staff reconciliation) which is the only thing that ever sets `paid` — the dashboard can now tell "cash in the rider's hand" from "cash reconciled with the business" instead of both looking identical.

**"Failed delivery," "customer refused," and "return to seller" are real, queryable outcomes, not just a `note` field.** New `PaymentService::markCodFailed()`/`markCodReturned()` methods (both `cod.collect`/`cod.manage`-gated, both idempotent) move a COD record to `failed_collection`/`returned` and its payment to `failed` — a `returned` payment is never silently marked `paid` because cash never changed hands, and a *return* on an order whose payment somehow already settled never gets downgraded. `DeliveryController::updateStatus()` gained a `delivery_attempts` counter (incremented every time a delivery re-enters `out_for_delivery`) and a required `failure_reason` whenever a delivery is marked `failed`/`returned` — and a `returned` delivery on a COD order now automatically calls `markCodReturned()`, so staff don't have to separately remember to update the payment side when a parcel comes back.

**Inventory has an actual sell-through lifecycle now, not just a hold that was created but never resolved.** Reading the reservation code closely surfaced a real gap: `inventory_reservations.status` had a `committed` value that nothing ever set, and `quantity_on_hand` never decreased when an order was actually delivered — there was no way to answer "how much have we sold" at all. The new `InventoryService` (`reserve → commit → release`/`fulfill`) is the single place stock is read or changed, and every method locks its rows (`lockForUpdate()`, inside a transaction) before checking availability, so two concurrent checkouts racing for the last unit of stock can't both succeed — the loser's transaction blocks until the winner's commits, then re-reads a figure that already accounts for it. `fulfill()` is what actually answers "Sold stock": it permanently decrements `quantity_on_hand` and marks the reservation `fulfilled`, called automatically when `OrderService` marks an order `delivered`. Every reservation/commit/release/sale/manual-adjustment writes an `inventory_movements` row (a new, dedicated append-only table — "Inventory history," separate from the generic `audit_logs` table that mixes every admin action across every module) via a new `GET /inventory/{id}/history` endpoint and an admin "History" view.

**Payment methods are backend configuration, never a schema decision — and nothing sensitive ever reaches the frontend.** `backend/config/payments.php` lists the allow-listed `methods` (`cod`, `easypaisa`, `jazzcash` today) and which of them are COD-like; `StoreOrderRequest` validates against that list via `Rule::in(...)`, so adding a "future payment gateway" is a one-line config change, never a migration. Only `cod` is a live, working flow: selecting Easypaisa or JazzCash at checkout is possible (the checkout page's new payment-method selector shows them, disabled, labeled "Coming soon" — no fake OTP/redirect UI was built) and creates a `Payment` row at the generic `pending` status, but there is no live gateway integration — no API keys exist for one, and CLAUDE.md §5/§6 are explicit that none would ever live in frontend code regardless. `payments`/`payment_transactions` have never stored anything beyond a gateway name and its own opaque reference token (asserted directly by a new schema test: `pin`/`otp`/`password`/`card_number`/`cvv`/`api_secret`/`api_key` must never exist as columns on `payments`), and `AiToolService`'s docblock now says explicitly, not just implicitly, that payment/COD verification is permanently out of its allow-list — `get_order_status` only ever answers with `orders.status`, never touches `payments`/`cod_records` at all.

**Every payment-sensitive mutation is idempotent, including two that weren't before.** Refunds already were (Phase 04); COD collect/verify were not — a retried request (a flaky connection, a rider double-tapping "confirm") would have double-processed. All four COD actions (`collect`, `verify`, and the two new ones, `fail`/`return`) now require an `Idempotency-Key` header via the same `idempotent` middleware, and the frontend's `lib/api/admin/payments.ts` generates a fresh key per click, mirroring the existing refund pattern.

**Concurrency is tested as a check-then-act guard, not literal parallel threads.** PHPUnit is single-threaded, so "two requests racing" is tested the way it actually matters in production: two sequential calls with genuinely different actors/idempotency keys (so neither short-circuits into an idempotent replay), asserting the *second* is rejected by the state check inside the transaction — `test_two_reservations_racing_for_the_last_units_the_second_is_rejected` (inventory) and `test_two_concurrent_collect_attempts_with_different_keys_the_second_is_rejected` (COD collection) are the two direct examples. This is the same guarantee `lockForUpdate()` provides under real parallel requests; the tests exercise the guard logic itself, which is identical either way.

**A real bug caught by manual code review, not a test run — again.** This session's sandbox still has no PHP 8.4+ runtime (see the note below), so every one of this phase's 32 new tests was traced by hand instead of executed. That trace caught a genuine bug: `UpdateOrderStatusRequest`'s validation rule hardcoded `in:confirmed,processing,dispatched,delivered,cancelled,refunded` — a leftover from before this phase added `ready`/`completed` to `OrderService::TRANSITIONS`. Every new order-lifecycle test would have failed at the validation layer with a 422 before ever reaching the service logic being tested, silently masking whether the actual transition graph worked at all. Fixed by updating the allow-list to match the service's real vocabulary.

Verify backend with `cd backend && php artisan test` (PHP 8.4+ required) — 32 new tests (9 in `PaymentTest`: payment-status separation on collect/fail/return, permission checks, idempotent-replay and concurrent-collect-rejection, and the no-raw-credentials schema assertion; 10 in `InventoryTest`: the full reserve/commit/release/fulfill lifecycle, the reservation-race rejection, and history recording; 5 in `DeliveryTest`: attempt counting, required failure reasons, and the COD-return sync; 8 in `OrderTest`: the full lifecycle through `completed`, the confirm/deliver/cancel side effects on payment and inventory, and payment-method config validation) — 222 backend tests total. Every file touched was also run through `php -l` (syntax-only, using a PHP 8.1 binary present in this sandbox) and came back clean — a partial but genuine verification step beyond pure reading, on top of the manual trace. Verify frontend with `cd frontend && npm run typecheck && npm run lint && npm run test && npm run build` — all four pass, 1 new test (63 total: array-valued `filter[col][]=` query-string building, which the new admin dashboard filter tabs depend on). Manually verified in a browser: admin pages correctly redirect to `/login?redirect=...` without a live session (expected, since the backend can't run here), and the checkout page's new payment-method selector renders with Easypaisa/JazzCash visibly present but disabled.

## Customer CRM, Reviews & Notifications (Phase 10)

Built in Phase 10, on top of the Phase 02 schema and the Phase 04/06/08 customer/review/notification infrastructure that already existed in outline. See [ADR 0010](docs/adr/0010-customer-crm-and-notifications.md) for the full reasoning; this is the short version.

**Customer profiles, order history, and addresses were already built (Phase 02/04/06/08) — this phase closed three real gaps: notes, tags, and a working notification pipeline.** `Customer`/`Address` and their full CRUD/RBAC already existed; the admin Customer detail screen just gained an order-history list (`GET /orders?filter[customer_id]=`, already supported, simply not surfaced there before) alongside what's genuinely new below.

**Staff notes are now a structured, append-only log, not just one overwritable field.** `customers.notes` (Phase 02) is a single text field — useful as a quick-glance summary, but it can't answer "who said what, when," and overwriting it discards history. `customer_notes` (new) is a separate, append-only table (no `updated_at`, matching `inventory_movements`'s own precedent for "this is a history log, not an editable record") — every note is timestamped and attributed to the staff member who wrote it, and can be added but never edited or deleted. Both coexist deliberately: the single field is unchanged, the new table is the real CRM log.

**Tags are a new, admin-curated classification system, with RBAC that's deliberately different from notes.** `customer_tags` (a small reference table, e.g. "VIP," "Wholesale," "Flagged") plus `customer_tag_assignments` (who tagged whom, when) let staff label and filter customers (`GET /customers?filter[tag_id]=`) without free text. Because tags are a bounded, admin-curated vocabulary rather than free-text commentary, reading a customer's tags only needs `customers.view` (useful for view-only `support` staff triaging a case); assigning or removing one still needs `customers.manage` — a deliberate asymmetry with the free-text notes above, which stay `customers.manage`-only to read or write, matching CLAUDE.md §4's "match exposure to actual sensitivity."

**Ratings now reflect every approved review, not just whatever page happened to load.** The storefront's review list computed its "average rating" client-side from only the 10 most recently fetched reviews — silently wrong for any product with more reviews than that. `ProductController::show()` now aggregates `rating_average`/`rating_count` server-side across every approved review; the product page and `ReviewList` use that real figure, falling back to the old partial-page computation only if the server didn't supply one.

**Order/payment/delivery notifications are a real trigger → template → channel pipeline now, not just an inbox nobody wrote to.** `GET/PATCH /notifications` (Phase 04) already let a user read their own notifications, but nothing ever created one. `OrderService::create()`/`transitionStatus()`, `PaymentService`'s refund/collect/verify/fail/return methods, and `DeliveryController::updateStatus()` each now notify the order's customer through the state change they already own — four new `Notification` classes (`OrderPlaced`, `OrderStatusChanged`, `PaymentStatusChanged`, `DeliveryStatusChanged`) sharing one base for channel selection and rendering. Every dispatch is wrapped and logged rather than allowed to fail the underlying order/payment/delivery mutation (CLAUDE.md §16) — a flaky mail send can never block a rider from marking a delivery out for delivery.

**Notification templates are real, admin-editable content, not hardcoded strings.** `notification_templates` holds one row per (event key, channel) pair — `order.placed`, `order.status_changed`, `payment.status_changed`, `delivery.status_changed`, each across `database`/`mail`/`whatsapp` (12 seeded rows) — with `{placeholder}` interpolation (`NotificationTemplateService`) against the data each event supplies. A missing or deactivated template falls back to a safe hardcoded message rather than sending nothing. The new `/admin/notification-templates` screen (gated by a new `notifications.manage` permission, granted to `manager`/`super_admin`) edits subject/body/active — there's deliberately no create/delete, since the set of valid (key, channel) pairs is fixed by what the Notification classes actually look up.

**WhatsApp is prepared, not built — the same posture Phase 09 took on Easypaisa/JazzCash.** No WhatsApp Business API account or credentials exist, so `WhatsAppChannel` never makes an outbound call — it logs the fully-rendered message and returns, gated behind `WHATSAPP_ENABLED` (defaults `false`). The trigger points, the template pipeline, and every notification's `toWhatsApp()` payload are real and exercised end to end; only the final "call a real provider" step is a deliberate no-op. Email is further along by comparison: Laravel's `mail` channel is genuinely wired (`MAIL_MAILER=log` by default, so a send really renders, just to the log instead of a real inbox).

**Customer data's exclusion from the AI agent is now written down, not just structurally true.** `AiToolService` never had a tool touching `customers`, `addresses`, `customer_notes`, or `customer_tags` — true by omission before this phase, the same state payment/COD verification was in before [ADR 0009](docs/adr/0009-payment-cod-inventory-delivery.md). The docblock now says so explicitly, and calls out that `get_order_status`'s hardcoded `order_number`/`status`-only return shape is a deliberate PII exclusion, not an accident of what happened to be implemented.

Verify backend with `cd backend && php artisan test` (PHP 8.4+ required) — 21 new tests (16 in `CustomerTest`: note/tag creation, append-only ordering, the notes-vs-tags RBAC asymmetry, tag filtering, and AI-agent exclusion; 9 in `ReviewTest` overall, 2 new: the true aggregated rating and the null-not-zero case with no approved reviews; 7 in `NotificationTemplateTest`: seeder idempotency, template CRUD RBAC, placeholder interpolation, and the hardcoded fallback when a template is missing; 2 new in `OrderTest` and 1 new in `DeliveryTest`: notification dispatch on order placement/status change/delivery update, plus an assertion added to `PaymentTest`'s existing COD-verification test) — 243 backend tests total. Every touched file was also run through `php -l` and came back clean, on top of the manual trace, for the same PHP 8.1-only sandbox reason as every prior phase. Verify frontend with `cd frontend && npm run typecheck && npm run lint && npm run test && npm run build` — all four pass (63 tests, unchanged — no new frontend unit tests this phase, the new pages/functions were exercised via typecheck/build/manual browser verification instead). Manually verified in a browser: `/admin/notification-templates` and `/account/notifications` both render and correctly redirect to their respective login pages without a live session, with no console errors beyond the expected "backend not running" fetch failures already documented in every prior phase.

## Media, Themes, Hero Banners, SEO & Social (Phase 11)

Built in Phase 11, on top of the Phase 04/06 media/content infrastructure that already existed in outline. See [ADR 0011](docs/adr/0011-media-themes-hero-banners-seo-social.md) for the full reasoning; this is the short version.

**One secure upload service, three real callers.** Product media upload already did everything CLAUDE.md §12 asks (genuine image validation via `getimagesize`, a server-side `mimes:jpeg,png,webp` allow-list, a size cap, a generated UUID filename never the client's own) — hero banners and category images previously only ever accepted a raw client-supplied URL string, which is not "secure image upload" by any meaningful definition. `MediaUploadService` extracts the "store a validated file, return its public URL" step into one place; `CategoryController::uploadImage()` and `HeroBannerController::uploadImage()` are new, dedicated endpoints built on it. The plain `image_url` columns still exist (an already-hosted/CDN image can still be linked directly), but the *secure* path is now a real upload for all three media types, not a text field.

**Hero banners: desktop and mobile are different crops, with a real CTA, reorder, and archive/restore.** `hero_banners` gained `mobile_image_url`, `alt_text`, and `cta_text` (paired with the existing `link_url`, so a CTA is now a labeled button, not just a bare link making the whole banner clickable). `image_url` (desktop) is now nullable — a banner is created text-first, then given its image via the upload endpoint, the same two-step flow product creation and product media upload already used. New endpoints: `show()` (single-banner preview), `uploadImage()` (either or both crops in one request — re-uploading *is* how an admin replaces an image), `reorder()` (the client sends the full desired id order; the server sets each `sort_order` to its position), and `restore()` (undoing the existing soft-delete-based archive). The admin Hero Banner Manager gained up/down reorder controls, an "Image" upload modal, a live preview panel (image + title/subtitle/CTA overlay), and an archived view with restore.

**Themes: a validated config shape, seeded twelve times over.** `Theme.config` was a bare `required|array` — nothing stopped a theme from being created missing half the fields the storefront needs to render it. `StoreThemeRequest`/`UpdateThemeRequest` now validate the full shape the business asked for: background/surface/text colors, primary/secondary brand colors, typography (body + heading font family), a font-size scale (`sm` through `2xl`), and button styling (corner radius, primary/secondary background+text). `ThemeSeeder` seeds twelve themes — Classic Chocolate, Midnight Cocoa, Rose Gold, Mint Fresh, Pastel Bakery, Royal Purple, Ocean Breeze, Autumn Spice, Monochrome, Berry Bliss, Golden Hour, Forest Green — each a real, distinct option and simultaneously a worked example of a valid config. `ThemeController` gained `show()` (preview a theme's full config without activating it), `update()` (previously impossible — only create and activate existed), and `deactivate()` (turn the active theme off without activating another, letting the storefront fall back to its own default styling). The admin Theme Manager now has a structured color/typography/font-size/button editor with a live-updating preview card, plus Edit and Deactivate actions that didn't exist before.

**SEO gained Open Graph as its own field, not silently reused meta copy.** `seo_metadata` had `og_image_url` but no `og_title`/`og_description` — a social share preview's title/description silently fell back to `meta_title`/`meta_description` with no way to write different copy for a share card specifically. Both are now independently editable in the shared `SeoSection` component (used by both the Category and Product managers). "SEO slug" is deliberately *not* a separate field — it's the entity's own `slug` column (Product/Category), edited where the entity itself is edited, since duplicating it into `seo_metadata` would create two sources of truth with nothing keeping them in sync.

**Facebook/Instagram are prepared, not built — the same posture Phase 10 took on WhatsApp and Phase 09 took on Easypaisa/JazzCash.** No Meta developer app or Instagram Business account exists, so there is no OAuth flow, no posting, no fetching. `GET /social/accounts` (new) reports `connected: true/false` per platform, derived from whether the required environment variables are populated — never a token or app secret, gated by `settings.manage` specifically (the RBAC permission CLAUDE.md §6 names for "integrations/secrets management"), not the broader `content.manage` most storefront-content staff hold. A new Settings panel shows the connection status. A dedicated test asserts a configured secret string never appears in the response body even when every credential is set.

## Database

**PostgreSQL**, designed for **Neon** initially. The backend's database connection is entirely environment-variable driven (`backend/config/database.php`'s `pgsql` connection, including `DB_SSLMODE` for Neon's required SSL) — the provider can be swapped (Neon → Railway Postgres → Supabase → self-hosted) without any code change, only environment variables. Accessed exclusively through the backend via Laravel's query builder/Eloquent. See [CLAUDE.md §22](CLAUDE.md#22-postgresql-database-architecture) for the governing access rules. No live database is connected yet — Neon/Railway Postgres provisioning happens in a later phase; today the schema only runs against the backend's SQLite test database.

### Schema (Phase 02)

42 domain tables (plus Laravel's own users/cache/jobs/notifications tables — 35 from Phase 02, `inventory_movements` in Phase 09, `customer_notes`/`customer_tags`/`customer_tag_assignments`/`notification_templates` in Phase 10, and `agent_pending_actions`/`agent_event_logs` in Phase 13), defined as migrations in [`backend/database/migrations/`](backend/database/migrations/) with a matching Eloquent model per table in [`backend/app/Models/`](backend/app/Models/). Grouped by concern:

- **Identity & access** — `users`, `roles`, `permissions`, and their pivots (`role_user`, `permission_role`), matching the RBAC roles in [CLAUDE.md §8](CLAUDE.md#8-rbac-role-based-access-control).
- **Customers** — `customers` (one per user account), `addresses`, `customer_notes` (Phase 10, append-only staff notes), `customer_tags`/`customer_tag_assignments` (Phase 10, admin-curated classification).
- **Catalog** — `categories` (self-referencing `parent_id` for a hierarchy of arbitrary depth), `products`, `category_product` (a product's canonical category is a column on `products`, but it can be tagged into any number of additional categories through this pivot — future-proof beyond a single-category model), `product_variants` (every product has ≥1 variant; price/SKU/stock all live at the variant level), `product_media`.
- **Inventory** — `inventory` (per variant, per location — a `location` column defaults to `'main'` today so multi-warehouse doesn't need a schema change later), `inventory_reservations` (holds through their full lifecycle — pending → committed → released/expired/**fulfilled** — available stock is always computed as `quantity_on_hand − active reservations`, never a separately-stored number that could drift), `inventory_movements` (Phase 09, append-only history of every reservation/commit/release/sale/manual adjustment, separate from the generic `audit_logs` table).
- **Delivery configuration** — `delivery_rules`, scoped `global` / `category` / `product` (enforced at the model layer — see below) so delivery eligibility and fees can be overridden per category or per product, with a `priority` column to resolve overlaps.
- **Orders** — `orders`, `order_items` (snapshots `product_name`/`sku`/price at time of purchase so a line item stays legible even if the product is later edited or deleted), `order_status_histories` (append-only log of every fulfillment-status transition).
- **Payments** — `payments`, `payment_transactions` (append-only ledger of charge/refund/chargeback attempts), `cod_records`.
- **Delivery fulfillment** — `deliveries`, `delivery_tracking_events` (append-only).
- **Marketing & content** — `coupons`, `coupon_scopes` (polymorphic — scopes a coupon to specific products/categories, or store-wide if empty), `reviews`, `hero_banners`, `themes`, `homepage_sections`, `seo_metadata` (polymorphic, one row per SEO-able entity).
- **Support & AI** — `notifications` (Laravel's standard polymorphic table, now actually written to as of Phase 10 - see [Customer CRM, Reviews & Notifications](#customer-crm-reviews--notifications-phase-10)), `notification_templates` (Phase 10, admin-editable copy per event/channel), `chat_conversations`, `chat_messages` (append-only transcript), `ai_usage_logs` (token/cost accounting per [CLAUDE.md §19](CLAUDE.md#19-cost--token-optimization) and the AI tool-call audit trail per [CLAUDE.md §9](CLAUDE.md#9-ai-security-and-guardrails), kept separate from the raw transcript), `agent_pending_actions` (Phase 13, the human-approval queue for high-risk agent tool calls), `agent_event_logs` (Phase 13, append-only, the 9-event feed a future agent's tools read instead of querying orders/payments/deliveries directly).
- **Governance** — `audit_logs` (append-only, immutable — see [CLAUDE.md §15](CLAUDE.md#15-audit-logging)), `system_settings` (configuration toggles only; secrets never live here, per [CLAUDE.md §6](CLAUDE.md#6-api-key-and-secret-management)).

**Design decisions worth calling out:**

- **Order status vs. payment status vs. COD status are three separate, independently-tracked state machines** on three separate tables (`orders.status`, `payments.status`, `cod_records.status`). Marking an order "dispatched" never touches payment state, and collecting COD cash never silently changes the order's fulfillment status — each transitions only when the code responsible for that concern says so.
- **No raw payment credentials anywhere.** `payments` stores only a gateway name and the gateway's own reference/token (per [CLAUDE.md §5](CLAUDE.md#5-payment-security)); passwords are hashed via Laravel's `hashed` cast, never reversible.
- **Soft deletes** are enabled on entities where recoverability or audit history matters (`users`, `customers`, `addresses`, `categories`, `products`, `product_variants`, `orders`, `payments`, `deliveries`, `coupons`, `reviews`, …) and deliberately omitted on append-only/immutable tables (`audit_logs`, `order_status_histories`, `payment_transactions`, `delivery_tracking_events`, `chat_messages`, `ai_usage_logs`) — those are never edited or deleted at the application level in the first place.
- **A few structural rules are enforced at the Eloquent model layer instead of a database CHECK constraint**, specifically so the schema stays portable across Postgres and the SQLite database used in tests (a goal directly requested by [CLAUDE.md §22](CLAUDE.md#22-postgresql-database-architecture)'s provider-swap requirement): `DeliveryRule` validates that its `scope` matches whichever of `category_id`/`product_id` is set, and `Theme` enforces "only one active theme" on save. Both are documented in the model source.
- **`orders.status`, `payments.status`, and `inventory_reservations.status` are plain indexed strings, not native DB enums** (Phase 09) — the same "business decision, not a fixed set" reasoning `payments.method` was already built on. `deliveries.status`/`cod_records.status` are still native enums; their vocabularies haven't needed to grow yet, and there's no principled objection to converting them too the day they do.
- **JSON columns use Laravel's portable `json` type**, not Postgres-specific `jsonb`. This can be upgraded per-column via a follow-up Postgres migration later if a specific column needs indexed JSON queries — not needed yet.
- **Structured staff notes and tags are separate tables from the profile fields they annotate** (Phase 10) — `customer_notes` is append-only (no `updated_at`) so a note's history can never be silently rewritten, and `customer_tags`/`customer_tag_assignments` keep the label vocabulary admin-curated rather than free text, which is what lets the two features carry different RBAC defaults (see [Customer CRM, Reviews & Notifications](#customer-crm-reviews--notifications-phase-10)).
- **`hero_banners.image_url` became nullable** (Phase 11) — a banner is now created text-first, then given its image via the secure upload endpoint, so creation can no longer require a URL up front. Dropped and re-added rather than `->nullable()->change()`, the same doctrine/dbal constraint every enum-to-string conversion in Phase 09 hit.
- **`chat_conversations.summary`** (Phase 12) — a deterministic, bounded compaction of a conversation's older messages, refreshed by `ChatSummarizationService` once the message count passes the verbatim-history window, so the AI is never sent the full transcript on every request (see [AI Chatbot](#ai-chatbot-phase-12)).
- **`users.agent_type`** (Phase 13) — which of the 8 named future agents an `ai_agent`-typed identity is provisioned as, scoping which tools it may call. A plain nullable string, not a DB enum or eight new RBAC roles - see [Future AI-Agent Architecture](#future-ai-agent-architecture-phase-13).

## Authentication & Security

Built in Phase 03, on top of the Phase 02 schema. See [ADR 0003](docs/adr/0003-authentication-and-authorization.md) for the full reasoning; this is the short version.

**Sessions.** CLAUDE.md §7's model exactly: a short-lived (15 min default) signed JWT access token plus a longer-lived (14 day default) opaque refresh token, both delivered as `httpOnly`, `Secure`, `SameSite` cookies — never in a JSON response body, never meant for `localStorage`. The JWT is verified with a hand-rolled HS256 implementation ([`app/Support/Jwt.php`](backend/app/Support/Jwt.php)) rather than a Composer package, because this sandbox has no outbound network access to install one — the algorithm is hardcoded on both sides, closing the "alg confusion" vulnerability class outright. The refresh token is stored hashed in a new `refresh_tokens` table and **rotates on every use**: reusing an already-rotated-out token is treated as a theft signal and revokes every other active session for that user, not just the reused one.

**CSRF.** A third cookie (`cc_csrf_token`, deliberately *not* `httpOnly`) plus an `X-CSRF-Token` header form a double-submit pair, checked on every state-changing request. This matters because the frontend (Vercel) and backend (Railway) are expected to live on different registrable domains by default — the auth cookies will likely need `SameSite=None` to be sent cross-site at all once the frontend origin is known, and `SameSite=None` alone provides no CSRF protection on its own.

**RBAC.** Roles and permissions (from the Phase 02 schema) are now enforced by centralized middleware (`role:...`, `permission:...`) on every route, not ad hoc checks in controllers. **AI agent identities are structurally kept out of the admin surface twice over**: a `users.type` column distinguishes `human` from `ai_agent` accounts, every `/admin/*` route additionally requires `type = human` regardless of permissions held, and the `ai.tools.use` permission is granted to the `ai_agent` role alone — excluded even from `super_admin`'s otherwise-full permission set, because it isn't an administrative capability.

**Provisioning.** No default admin account or password is ever seeded. The first `super_admin` (or any role grant) is assigned via `php artisan role:assign {email} {role}` — a CLI-only command, never an HTTP endpoint — against an already-registered account, with every grant written to the audit log.

**Also in place:** per-account+IP login rate limiting with lockout (`RateLimiter`, no extra infrastructure), bcrypt password hashing with a minimum-strength policy, strict security headers (CSP, `X-Frame-Options`, HSTS on secure requests) on every response, request validation via Form Request classes at every auth endpoint, and an `is_active` flag plus a `token_version` counter that lets a forced "log out everywhere" instantly invalidate a still-unexpired access token.

**MFA/2FA is prepared, not built.** `users` has encrypted `two_factor_secret`/`two_factor_recovery_codes`/`two_factor_confirmed_at` columns and the login flow already checks them, but returns `501 Not Implemented` — no TOTP library, QR enrollment, or SMS gateway exists yet. Deferred deliberately (no user can enable it yet, so building the verification endpoint now would be premature), but the hook point is real, not hypothetical.

Verify with `cd backend && php artisan test tests/Feature/Auth tests/Unit/Support/JwtTest.php` — 57 tests covering registration, login/lockout, logout, refresh/rotation/theft-detection, CSRF, security headers, and authorization boundaries for every role against every protected route (including the explicit "can a guest/customer/ai_agent reach an admin API" checks).

## Backend API

Built in Phase 04, on top of the Phase 02 schema and Phase 03 auth layer. See [ADR 0004](docs/adr/0004-api-foundation.md) for the full reasoning; this is the short version.

**19 modules, one application.** Users (staff), Categories, Products (with variants and media), Customers (with addresses), Inventory, Orders, Payments (with COD), Delivery, Reviews, Media (uploads), Themes, Homepage (sections and hero banners), SEO metadata, Notifications, Chat, AI tools, Analytics, Audit logs, and Settings — each a Controller + Form Request(s) + API Resource(s) under `routes/api/{module}.php`, versioned under `/api/v1/...`. No microservices: one deployable, module boundaries are directories and namespaces, not network calls.

**Consistent everywhere.** Every success response is a Laravel API Resource (`{"data": ...}`, with `links`/`meta` on paginated lists) — never a raw database row. Every error, from every module, goes through one handler that normalizes validation/auth/not-found/server errors into `{"message": ..., "errors"?: ...}` and never leaks an Eloquent class name or stack trace. Listing endpoints share one reusable helper (`App\Support\Api\ApiQuery`) for pagination, `?filter[column]=`, `?sort=col,-col2`, and `?search=term` — each controller opts a specific column allow-list in, so a client can never filter or sort by an internal-only column.

**Idempotency where it matters.** CLAUDE.md §13 names payment-affecting and order-mutating endpoints specifically — placing an order, issuing a refund, and (Phase 09) every COD collect/verify/fail/return action all require an `Idempotency-Key` header; a retried request with the same key replays the original response instead of double-charging, double-ordering, or double-collecting.

**CSRF coverage is now consistent across every mutating module.** Phase 11 found and fixed a real, pre-existing gap: `/categories`, `/products`, and `/products/{id}/variants` mutations never had `csrf.cookie` applied, unlike every other module (payments, orders, customers, delivery, content, ...). Since the API is cookie-authenticated and the frontend/backend are expected to sit on different registrable domains eventually requiring `SameSite=None` (which alone provides no CSRF protection — see [Authentication & Security](#authentication--security)), this was a genuine gap, closed immediately per CLAUDE.md §2/§16 rather than deferred.

**Business logic lives in services, not controllers.** Checkout (`OrderService`) computes pricing server-side from the live variant price, resolves delivery fees from the Phase 02 `delivery_rules` table, validates coupons, reserves inventory (via `InventoryService`, Phase 09), and enforces an explicit order-status transition graph whose side effects touch payment/inventory status only at the points the business flow itself implies (confirm → commit reservations + `cod_confirmed`; deliver → fulfill reservations, i.e. "sold"; cancel → release reservations + `cancelled`, never downgrading an already-paid payment) — and, since Phase 10, notifies the customer on order placement and every status change. `InventoryService` (Phase 09) is the single place stock is read or changed — every mutation is a row-locked transaction, so concurrent checkouts can't oversell the last unit. `PaymentService` handles refunds (capped at what's actually left to refund) and the COD collect → verify → fail/return flow, where only staff *verification* — not the rider's own collection claim — flips a payment to paid, notifying the customer on every one of those transitions too. `AgentToolGateway` (Phase 13, replacing the narrower pre-Phase-13 `AiToolService`) gives the `ai_agent` identity a fixed, schema-validated, allow-listed set of tools — two read-only ones open to any agent (check product availability, get order status), two more scoped by `agent_type` (inventory level, recent events), and two high-risk ones (request a refund, request an order cancellation) that never execute immediately, only after a human approves — and logs every call, successful, refused, or errored. Customer data (profile, staff notes, tags) is entirely out of its reach, permanently and explicitly — `get_order_status`'s return shape is hardcoded to `order_number`/`status` only, deliberately excluding every PII field the underlying `Order` model actually has, and no tool anywhere accepts a free-form query. `AiChatService` (Phase 12, the customer-facing chatbot, which never calls `AgentToolGateway` at all) runs a separate intent-detection → deterministic-lookup → AI-only-when-necessary pipeline so prices/stock/delivery/hours/payment methods/order status/contact never cost a model call - see [AI Chatbot](#ai-chatbot-phase-12) and [Future AI-Agent Architecture](#future-ai-agent-architecture-phase-13).

**Authorization, layered.** Route-level `role:`/`permission:` middleware (Phase 03) gates whole classes of action; object-level Policies (`OrderPolicy`, `AddressPolicy`, `CustomerPolicy`, `DeliveryPolicy`, `PaymentPolicy`, `ChatConversationPolicy`) gate access to a *specific* row by ownership — a customer's own orders/addresses/profile/chat, a rider's own deliveries. Role *assignment* still has no HTTP endpoint at all (CLI-only, per Phase 03) — the new Users module lists staff and can activate/deactivate an account (which also instantly invalidates its live sessions), nothing more.

**Sensitive actions are audit-logged.** Order status changes, refunds, COD collection/verification, product/category/content changes, staff activation/deactivation, settings changes, (Phase 10) staff notes/tags added to a customer and notification-template edits, and (Phase 13) every agent tool request/approval/rejection all write to the append-only audit log via one call site (`AuditLogger::log()`), per CLAUDE.md §15.

**Two real bugs the tests caught, not just the endpoints:** Phase 02's `Relation::enforceMorphMap()` would have thrown on the first audit-logged action for any model outside its small original allow-list (fixed by switching to the non-enforced `morphMap()`); and two models' `#[Fillable(...)]` lists silently dropped fields the new controllers needed to set (`Review.is_approved`, `User.is_active`) — Laravel drops non-fillable mass-assignment keys without erroring, so both failed quietly until a test compared the response to the actual database state. Full detail, including why `User.is_active` was deliberately *not* just added to the fillable list, is in ADR 0004.

Verify with `cd backend && php artisan test` — 277 tests total across the whole backend (Phase 01 foundation + Phase 02 schema + Phase 03 auth + Phase 04's 85 module tests + Phase 06's 41 tests for the four gaps it found and closed + Phase 07's 11 tests for category/best-sellers/homepage-seeding behavior + Phase 08's 18 tests for delivery eligibility/checkout/tracking + Phase 09's 32 tests for payment/COD/inventory/delivery + Phase 10's 21 tests for customer notes/tags/RBAC, rating aggregation, and the notification pipeline + Phase 11's 34 tests for upload security, theme/hero-banner/SEO behavior, and social-integration RBAC — see [Admin Panel](#admin-panel), [Product Catalog & Homepage](#product-catalog--homepage-phase-07), [Cart, Checkout & Order Fulfillment](#cart-checkout--order-fulfillment-phase-08), [Payment, COD, Inventory & Delivery](#payment-cod-inventory--delivery-phase-09), [Customer CRM, Reviews & Notifications](#customer-crm-reviews--notifications-phase-10), and [Media, Themes, Hero Banners, SEO & Social](#media-themes-hero-banners-seo--social-phase-11)), each module covering both the authenticated/unauthenticated and authorized/unauthorized path, not just the happy one.

## AI Chatbot (Phase 12)

Built in Phase 12, on top of the `chat_conversations`/`chat_messages`/`ai_usage_logs` schema and the narrow, allow-listed `AiToolService` that already existed in outline since Phase 02/04/09/10 - what didn't exist yet was anything that actually generated a bot reply. `ChatController::sendMessage()` used to just store the customer's message and stop. See [ADR 0012](docs/adr/0012-ai-chatbot.md) for the full reasoning; this is the short version.

**The cost architecture is real code, not an instruction to "be careful."** `AiChatService::respond()` is the literal pipeline the business specified: `Customer Query → Intent Detection → Deterministic Backend Lookup where possible → Relevant Data Retrieval → AI only when necessary → Response`. `ChatIntentDetector` classifies a message with plain regex (deliberately not a model call - using AI to decide whether AI is needed would defeat the entire point). `ChatBackendLookupService` then either fully answers from real data or returns `null` - prices and stock (searched against the live `products`/`product_variants`/inventory data), delivery rules (the same `delivery_rules` table `OrderService` itself checks), business hours and contact details (seeded `system_settings`, editable through `/admin/settings`), payment methods (`config('payments.methods')`), and order status (scoped to the *asking customer's own orders only* - a customer typing a stranger's real order number learns nothing). Only past that point does the AI step even get involved, and even then `retrieveRelevantContext()` sends at most 3 short product snippets, never the catalog.

**Two independent rate/cost controls.** A `chat` rate limiter (15/min per user) caps request volume on the message endpoint regardless of cost; a separate, cost-specific circuit breaker (`AiChatService::aiCallBudgetExceeded()`) reads `ai_usage_logs` directly and stops a single conversation from triggering more than a configured number of *paid* model calls per hour, independent of general request volume. Every AI call also has a hard response-token ceiling (`services.anthropic.max_tokens`, enforced by the API itself).

**Context and conversation-history limits, with real (if deliberately simple) summarization.** Only the most recent N messages (`services.anthropic.max_history_messages`, default 8) are ever sent to the model verbatim - anything older is compacted by `ChatSummarizationService` into one bounded summary string (`chat_conversations.summary`) instead of resending the full transcript on every request. Summarization is deterministic string truncation, not a second AI call - summarizing with a model would mean paying to save money.

**A real AI provider that gracefully degrades, not a stub.** No `ANTHROPIC_API_KEY` is configured in any environment yet (the same "prepared" posture Phase 10/11 used for WhatsApp/Facebook/Instagram) - but unlike those, the chatbot needs to work today, so only the "AI is genuinely necessary" branch is affected: `AnthropicChatProvider` throws immediately with no key configured, before any network call, and `AiChatService` catches that and returns a safe, honest fallback reply. Both branches are real, tested code - the no-key fallback path is exercised directly, and the working-provider path is exercised too, via `Http::fake()` simulating an actual Anthropic response.

**Prompt injection: structural first, pattern-matching second, output-scanning third.** User text is always sent as a `user`-role message in the API's own structured `messages` array, never concatenated into the system prompt string - the actual guarantee (CLAUDE.md §10), not just an instruction. `PromptInjectionGuard` additionally pattern-matches common override/jailbreak phrasing and routes a flagged message down the deterministic-reply path instead of ever reaching the paid model (a security control and a cost control at once), and scans every AI reply for anything shaped like a real credential before it reaches the customer, regardless of what the model said - a hard, code-enforced backstop, since model behavior is probabilistic and the system prompt's own instructions aren't a guarantee. A dedicated test inspects the actual outbound HTTP request body to confirm a configured API key never appears in the prompt text sent to the model, only in the request header.

**The system prompt explicitly, permanently forbids revealing itself, secrets, or internal tools - and there's nothing for it to reveal even if it tried.** The chatbot's AI step is a single bounded completion per reply; it does not do model-driven tool-calling and has no path to `AiToolService`, the database, or any admin surface. Everything the model can talk about is either the fixed system-prompt instructions or the handful of pre-fetched, bounded product snippets `retrieveRelevantContext()` supplies - never a raw query result, never customer or staff data.

**Cost monitoring is a real admin screen.** `GET /analytics/ai-usage` (new, `analytics.view`-gated) aggregates `ai_usage_logs` into total replies, total cost, a provider breakdown (`internal` vs `anthropic` - the deterministic/AI split the whole architecture exists to maximize), and a status breakdown. Deterministic replies are logged too, at zero cost, specifically so the split is visible rather than only ever showing AI spend in isolation. A new `/admin/ai-usage` page renders it.

**The widget itself.** A floating chat button on every storefront page (`ChatWidget`, gated behind customer login - matching `ChatController::store()`'s existing requirement that a conversation belongs to a `Customer`; anonymous chat is a separate, larger auth change this phase wasn't asked to make). A conversation is created lazily on the first message sent, not just from opening the widget, so browsing customers who never actually chat don't leave behind empty conversation rows.

**A real bug caught by manual code review, not a test run.** The first draft of the AI-call path built the bounded history (which already includes the customer's just-persisted message as its last entry) and then appended that same message a second time before sending it to the model - harmless to correctness, but directly wasteful of the tokens this phase exists to minimize. Caught by tracing exactly what `buildHistory()`'s query returns against what the controller had already saved, not by running the code (this session's sandbox still has no PHP 8.4+ runtime). Fixed by removing the redundant append, with a secondary `orderBy('id')` added to both `AiChatService` and `ChatSummarizationService` so they agree on the exact same "recent vs. summarized" boundary even when messages share a timestamp.

Verify backend with `cd backend && php artisan test` (PHP 8.4+ required) — 22 new tests (19 in the new `ChatBotTest`: every deterministic intent, the order-status ownership check, prompt-injection deflection, the no-key graceful fallback, a mocked successful AI call with cost logging, the API-key-never-in-prompt assertion, the AI budget circuit breaker, chat rate limiting, and summarization behavior; 3 in the new `AiUsageAnalyticsTest`: RBAC and the cost/status breakdown shape) — 300 backend tests total. Every touched file was also run through `php -l` and came back clean, on top of the manual trace, for the same PHP 8.1-only sandbox reason as every prior phase. Verify frontend with `cd frontend && npm run typecheck && npm run lint && npm run test && npm run build` — all four pass (63 tests, unchanged - the new widget and dashboard were exercised via typecheck/build/manual browser verification instead of new unit tests). ## Future AI-Agent Architecture (Phase 13)

Built in Phase 13, on top of the narrower Phase 04/09/10/12 tool-invocation surface (`check_product_availability`/`get_order_status`, used by the customer chatbot's own tool needs). This phase built the *architecture* eight future named agents — Sales, Customer Support, Order, Payment, Inventory, Marketing, Dispatch, Analytics — will eventually use, deliberately without building any of them: "Do not build unnecessary AI agents now. Only create the architecture and safe interfaces." See [ADR 0013](docs/adr/0013-ai-agent-architecture.md) for the full reasoning; this is the short version.

**One gateway, the exact pipeline specified.** `AgentToolGateway` implements `Agent → Approved Tool → Validation → Authorization → Business Logic → Database` as real code: resolve the named tool from a fixed registry (unknown name = refused), validate input against the tool's own strict schema, check the calling identity's `agent_type` against the tool's allow-list, then — and only then — call the tool's business logic, which itself only ever delegates to an existing Service (`OrderService`, `PaymentService`, `InventoryService`, ...) or a narrowly-scoped read query. There is no code path from an agent to raw SQL or an unscoped query — "agents must not directly access the database" is a structural guarantee, not a convention. `AiToolService` (the pre-Phase-13 tool surface) is retired; `POST /ai/tools/invoke` is unchanged and every one of its existing tests still passes, because the endpoint's contract never moved.

**`users.agent_type` scopes tools per agent, without provisioning eight new roles.** A new nullable column (not a DB enum — the same "business decision, not a fixed set" reasoning `payments.method` already established) records which of the 8 named types an `ai_agent`-typed identity is. Each tool declares its own `allowedAgentTypes()` — empty means unrestricted, preserving exact backward compatibility for the two pre-existing tools. `php artisan agent:provision {email} {agent_type}` (CLI-only, same trust boundary as `role:assign`) is the only way to set it; the command existing doesn't mean any agent has been provisioned.

**Strict schemas, enforced before anything resembling business logic runs.** Every tool declares Laravel validation rules (`AgentToolInterface::rules()`) checked immediately after authorization — a malformed or malicious-shaped request (including a SQL-injection-shaped string) is just an ordinary validation failure, logged as `refused`, never reaching a query.

**High-risk operations require human approval — a real queue, not a warning label.** Two of the business's seven named high-risk categories (Refund, Order cancellation) have working tools (`request_refund`, `request_order_cancellation`) that prove the mechanism end-to-end; the other five (payment verification, large discount, price changes, bulk deletion, dispatch cancellation) are classified in the architecture but have no tool yet — "only create the architecture and safe interfaces." A high-risk tool call never executes — it creates an `agent_pending_actions` row instead, and only a human reviewer's explicit approval (`AgentApprovalService::approve()`) runs the underlying business logic, atomically with recording the outcome. Approving requires *both* a new `agent_actions.manage` permission (visibility into the queue, `manager`/`super_admin`) *and* the specific domain permission the action itself would need directly (`orders.refund` for a refund, `orders.manage` for a cancellation) — not one blanket "can approve anything" gate. The reviewing human becomes the accountable actor in the resulting audit trail, not "the AI." A new `/admin/agent-actions` screen lets staff review, approve, and reject.

**Event architecture: 9 named events, one listener, nothing reacts yet.** `ORDER_CREATED`, `PAYMENT_SUBMITTED`, `PAYMENT_VERIFIED`, `ORDER_CONFIRMED`, `ORDER_READY`, `ORDER_DISPATCHED`, `ORDER_DELIVERED`, `ORDER_CANCELLED`, and `REFUND_COMPLETED` each dispatch from the exact point in `OrderService`/`OrderController`/`PaymentService` where that transition already happens — no new business logic, just making it observable. Every event carries only compact scalar identifiers, never a serialized model (the same token-cost discipline Phase 12's chatbot context already established). `LogAgentEvent`, the only subscriber, writes a compact row to a new `agent_event_logs` table — the durable feed a future agent's `get_recent_events` tool reads from instead of ever querying `orders`/`payments`/`deliveries` directly. Building a listener that actually *reacts* to these (auto-assigning a dispatch agent, alerting an analytics agent) would be building an agent, not architecture — deliberately not done.

**Two real bugs caught by manual code review.** `AgentApprovalService::approve()`'s first draft wrapped the whole method in a database transaction, including the `catch` block recording a failure — but a caught exception still rolls back the transaction it was thrown inside, so that failure record would itself have been silently discarded every time, defeating the entire point of catching it. Fixed by removing the outer transaction (the underlying `PaymentService`/`OrderService` calls already manage their own). Separately, the low-risk execution path had no error handling around a tool's business logic at all — an unexpected failure would leave no audit trail whatsoever, the exact calls most worth auditing. Fixed by catching, logging `status='error'`, and re-throwing.

Verify backend with `cd backend && php artisan test` (PHP 8.4+ required) — 25 new tests (11 in the new `AgentToolGatewayTest`: agent-type authorization scoping, high-risk requests never executing immediately, unregistered-tool/invalid-schema refusal, and SQL-injection-shaped input handled safely; 9 in the new `AgentApprovalTest`: the double-permission approval gate, no double-processing, rejection never executing, and a failure-at-approval-time being recorded correctly; 5 in the new `AgentEventArchitectureTest`: every named event logging correctly, real trigger points firing them, and `get_recent_events` reading the feed bounded and scoped) — 325 backend tests total. Every touched file was also run through `php -l` and came back clean, on top of the manual trace, for the same PHP 8.1-only sandbox reason as every prior phase. Verify frontend with `cd frontend && npm run typecheck && npm run lint && npm run test && npm run build` — all four pass (63 tests, unchanged — the new review screen was exercised via typecheck/build/manual browser verification instead of new unit tests). ## Analytics, Audit Logging & AI Cost Governance (Phase 14)

Built in Phase 14, on top of the `AnalyticsController` (overview/sales/ai-usage only), `AuditLogger`, and `ai_usage_logs`/`AgentToolGateway` infrastructure that already existed from Phases 04/09/12/13. What didn't exist yet was operational reporting beyond three endpoints, a code-level backstop against ever logging a secret, or any usage cap on the agent tool-call surface at all. See [ADR 0014](docs/adr/0014-analytics-audit-and-ai-cost-governance.md) for the full reasoning; this is the short version.

**Eight new analytics endpoints, extracted into a real service this time.** `AnalyticsController`'s own original docblock named its exit condition - "a dedicated reporting service becomes worth it once a concrete need... shows up" - and eleven aggregation methods inline in a controller was that concrete need. `AnalyticsService` now holds all of it: order analytics (status mix, average order value, cancellation rate), product performance and best sellers (the same real-sales-data definition the storefront's own best-sellers section uses, admin-scoped with revenue and a date range), customer metrics (new vs. repeat customers, top spenders), COD success rate and failed delivery rate (both computed over *resolved* records only - a still-`awaiting_delivery` COD record or an in-transit delivery is excluded from the rate rather than silently counted as a failure), a point-in-time inventory snapshot (out-of-stock/low-stock, accounting for active reservations the same way `InventoryService::availableQuantity()` does), and payment analytics by method with failure/refund rates. Permission gating (`analytics.view`) moved from a repeated inline `abort_unless` in every controller method to one `permission:analytics.view` route-group middleware - CLAUDE.md §8's "centralized, not scattered ad hoc" - with identical external behavior confirmed by the pre-existing `GovernanceTest` RBAC test passing unchanged.

**Audit logging gained a code-level redaction backstop, not just "the models don't have those columns."** `AuditLogger::log()` now recursively strips any key matching a fixed denylist (password, api_key, otp, cvv, card_number, two_factor_secret, and more) from every `before`/`after` snapshot before it's ever written, case-insensitively and at any nesting depth. Today this never actually fires - payments/payment_transactions have their own schema test asserting they can't hold these fields - but relying solely on that was exactly the kind of implicit guarantee that breaks silently the day someone adds a field without thinking about it. Auth events (login success/failure/lockout-adjacent, logout, registration, CLI role assignment) already flowed into `audit_logs` since Phase 03; **security events** now do too - a detected prompt-injection attempt (`PromptInjectionGuard::scanInbound()`) writes a durable `security.prompt_injection_detected` audit row (a bounded excerpt, not the full message) in addition to the existing application-log line, so a `super_admin` reviewing the audit trail sees it without grepping server logs. AI tool calls and agent actions continue to be audited through `ai_usage_logs` (every call, successful or refused) and `audit_logs` (every approval/rejection) respectively - the two-table split from Phase 13, not duplicated into a third place.

**Configurable usage limits, generalized from a chat-only check to a real cross-cutting service.** `AiUsageLimiter` centralizes what used to be one private method on `AiChatService`: the existing per-conversation-per-hour cap, a new per-agent-identity hourly cap on the Phase 13 tool-call surface (which had *no* volume limit at all before this - an allow-listed but low-risk tool like `check_product_availability` could otherwise be called without bound), and two new global daily caps (cost and request-count, both disabled at 0 by default since no live Anthropic key exists in any environment yet). `AgentToolGateway::invoke()` now checks the limiter before the registry lookup even runs, refusing and logging exactly like an unknown tool or a schema failure would. `GET /analytics/ai-usage` was extended (same endpoint, new fields - nothing removed) with token totals, a per-model breakdown, a per-purpose breakdown (chat replies vs. agent tool calls), a per-agent-type breakdown (joined through `users.agent_type`), and a `limits` block showing every configured cap next to today's actual usage against it - a limit nobody can see against reality isn't really "monitoring."

**Tests were actually executed this phase, for the first time in this project's history - and found two real, pre-existing bugs.** Every prior phase's own text says its tests were "written and manually traced but not executed" because the sandbox only had PHP 8.1 while the resolved Composer lock needs 8.4.1+. This phase installed PHP 8.4 (via `winget`, alongside the existing PHP 8.1 without touching its PATH) and ran the full suite for real: 340 of 359 passed. ## Security Architecture

Security is layered across every tier: RBAC-gated backend routes, CSRF double-submit protection on every state-changing route (a real, pre-existing gap on category/product mutations was found and closed in Phase 11 — see [Media, Themes, Hero Banners, SEO & Social](#media-themes-hero-banners-seo--social-phase-11)), input validation at the API boundary, secure file upload with server-side MIME validation and generated filenames (CLAUDE.md §12), no secrets in client code or version control, PCI-conscious payment handling (no raw card data ever touches our systems), rate limiting on sensitive endpoints (including two independent layers on the chatbot specifically — request-volume and AI-cost — Phase 12), prompt-injection defense in depth for the AI chatbot (structured message roles, inbound pattern-matching, outbound secret-shape redaction — see [AI Chatbot](#ai-chatbot-phase-12)), no AI-agent identity able to reach the database directly (every tool call routes through validated, authorized, allow-listed business logic — Phase 13) with high-risk operations gated behind human approval requiring the same domain permission the action itself would need, audit logging of every state-changing admin action with a code-level redaction backstop against ever persisting a password/API key/OTP/payment credential regardless of what a future model gains (Phase 14), durable security-event logging (prompt-injection detections, alongside the existing auth-event logging), and configurable, enforced usage limits on every AI-touching surface — chat and agent tool calls alike — not just the chatbot (Phase 14). Phase 15 ran a full security audit against this posture (`SECURITY_AUDIT.md`) and closed every Critical/High gap it found: a race in the idempotency middleware that could let a duplicate request double-process a payment-affecting action, CSRF gaps on the customer address book and inventory-mutation routes, an uploaded file's stored extension trusting the client-supplied filename instead of validated content, product descriptions reaching the AI system prompt without being scanned for injection attempts the same way customer chat messages already are, a debug-mode code path that could leak a stack trace to an API client, and — the one HTML-serving surface in the stack — the frontend previously shipping zero security headers of its own, now carrying CSP/`X-Frame-Options`/`Referrer-Policy`/`Permissions-Policy`. 6 Medium and 7 Low findings remain open and documented with a recommended fix each. The full rule set lives in [CLAUDE.md](CLAUDE.md) (§3–§17, §23) and is treated as non-negotiable baseline, not aspirational.

## Testing Strategy

Unit tests for business logic (pricing, delivery rules, order state machine, RBAC checks), integration tests for API endpoints (including authorization-denied paths, not just happy paths), and end-to-end tests for critical journeys (checkout, admin order management) before those flows ship. Full detail in [CLAUDE.md §18](CLAUDE.md#18-testing-requirements).

`backend/` runs PHPUnit (`php artisan test`) against an in-memory SQLite database, independent of the runtime Postgres connection; `frontend/` runs Vitest + React Testing Library (`npm run test`), plus `npm run typecheck`, `npm run lint`, and `npm run build` as part of every phase's validation. The backend suite covers the database schema (Phase 02), the auth/security layer (Phase 03), every API module (Phase 04), the four gaps Phase 06 closed, Phase 07's category/best-sellers/homepage-seeding behavior, Phase 08's delivery-eligibility/checkout/tracking behavior, Phase 09's payment-status-separation/COD/inventory-lifecycle/concurrency behavior, Phase 10's customer-notes/tags-RBAC, rating-aggregation, and notification-pipeline behavior, Phase 11's upload-security/theme/hero-banner/SEO/social-RBAC behavior, Phase 12's chatbot pipeline/prompt-injection/cost-control behavior, Phase 13's agent-tool-authorization/high-risk-approval/event-architecture behavior, Phase 14's analytics/audit-redaction/usage-limit behavior, and Phase 15's security-hardening/regression fixes — one test file per module under `tests/Feature/{Module}/`, each covering the authenticated/unauthenticated and authorized/unauthorized path per [CLAUDE.md §18](CLAUDE.md#18-testing-requirements), not just the happy path.

**361 backend tests total, 361 passing — both fully green.** Phase 14 was the first phase to actually execute the suite (installing PHP 8.4 via `winget`, since the sandbox previously only had PHP 8.1 against a Composer lock requiring 8.4.1+) rather than only writing and manually tracing tests as every prior phase had; that first real run surfaced 19 failures accumulated invisibly across 13 phases. Phase 15 investigated and fixed all 19 — none were security vulnerabilities (`SECURITY_AUDIT.md` covers those separately): two real regex bugs in `ChatIntentDetector` (a missing plural `s` on "payment method(s)", and no pattern for "status **of** order X" phrasing), two test files missing a `withCredentials()` call that every CSRF-testing suite in this codebase otherwise makes, `GET /themes/{theme}` inconsistently gated behind auth despite the identical data already being public via the theme list endpoint, a missing `orderBy('id')` tiebreaker on customer notes sharing a timestamp (the same class of bug `ChatSummarizationService` already had a documented fix for), and two test-setup gaps (a stale float-vs-int JSON assertion, a test missing its `Customer` profile fixture). Full detail, file-by-file, is in `QA_REPORT.md`. Phase 15 also closed 5 High-severity and 3 Medium-severity findings from its own security audit (`SECURITY_AUDIT.md`) — an idempotency race that could let a duplicate request double-process a refund/COD-collection, CSRF gaps on customer-address/inventory mutation routes, an upload path that trusted the client's filename extension for the stored file, product descriptions reaching the AI system prompt without being scanned for injection attempts, and a debug-mode code path that could leak a stack trace to an API client.

Every touched-or-added file across every phase was also confirmed with `php -l` as a syntax check. Phase 12's tests additionally use `Http::fake()` to exercise the real successful-AI-call code path against a simulated Anthropic response, without needing live network access. The frontend suite (63 tests) covers the Phase 05 storefront (API query/pagination helpers, product pricing/discount logic, route-building, component rendering), Phase 06's authorization-focused additions (permission-matrix logic, RBAC-based sidebar filtering, `RequirePermission` allow/deny, session-redirect behavior, the 401-refresh-retry flow), Phase 07's homepage-composition/search-filtering additions, Phase 08's cart/customer-auth-gate additions, and Phase 09's array-valued filter-query-string test — all of which pass; Phase 10 through Phase 15 added no new frontend unit tests (their new pages/functions were verified via `typecheck`/`lint`/`build` and manual browser checks instead, including confirming Phase 15's new CSP/security headers don't break the app - `script-src`/`style-src` need `'unsafe-inline'` for Next.js's own inline hydration scripts, confirmed by testing a stricter policy in a real browser first). ## Deployment Strategy

Frontend deploys to Vercel with preview deployments per pull request; backend deploys to Railway with separate staging and production environments. CI must pass (lint, typecheck, tests) before any deploy, database migrations run as a deliberate, reviewed step, and nothing is pushed to a shared branch or deployed without it being deployable and rollback-ready. Full detail in [CLAUDE.md §25](CLAUDE.md#25-deployment-principles).

No environment is connected yet — this foundation phase deliberately stops short of provisioning a Neon database, a Railway service, or a Vercel project, and nothing has been pushed to GitHub.
